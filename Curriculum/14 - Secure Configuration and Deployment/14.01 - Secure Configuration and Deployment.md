# Module 14 - Secure Configuration and Deployment

This outline defines the secure configuration and deployment knowledge assessed in Module 14.

## 14.1 Web server and file deployment

- Why the server, its configuration, and its deployment process are part of the application's attack surface
- The difference between files that are served to clients and files that must stay outside the web root, such as source code, configuration, backups, and version-control data
- Why uploaded files are stored apart from application code and static assets (see Module 12, section 12.7)
- Least-privilege file permissions: which identity may read, write, or execute application files
- Why the web server identity, the application identity, and the deployment identity are separate and have no more privileges than they need
- Why directory listing, unneeded HTTP methods, and exposed administrative interfaces are disabled or restricted
- Differences between test and production files and environments, and why test data, test accounts, and test endpoints do not reach production
- The risk of production data in test environments (see Module 8, section 8.4)

## 14.2 Platform-as-a-service and cloud deployment

- The shared responsibility model: what the platform provider secures and what the application team secures
- Platform settings the application team still owns: HTTPS enforcement, authentication, network restrictions, and application settings
- Managed identities and platform secret stores as alternatives to stored credentials
- Why remote access, management endpoints, and diagnostic features are disabled or restricted when not needed
- How deployment slots, staging environments, and preview environments can expose unfinished or unprotected versions of the application
- Why configuration for different environments is kept separate and access to each environment is limited
- The role of infrastructure as code in making configuration reviewable, repeatable, and testable

## 14.3 Packages and signing

- Risks of deploying packages, images, and updates from unverified sources
- What a digital signature on a package, image, or commit proves, and what it does not prove
- The differences between code signing, commit signing, and image signing
- Why the verifier must check the signer's identity against a trusted source, and why a valid signature from an unexpected signer is not trusted
- Why artifacts are verified before deployment and failed verification stops the deployment
- Lockfiles and hash pinning as integrity controls for deployed dependencies
- Provenance, and where it complements signatures (see Module 10, section 10.5)

## 14.4 Secure defaults

- Why default settings favor ease of setup over security
- Examples of insecure defaults: default credentials, sample applications, open management ports, verbose errors, permissive access, and enabled debug modes
- Why unnecessary features, sample files, documentation, components, and unused dependencies are removed before deployment
- Why debug code, debug endpoints, and development flags are absent or disabled in production
- Backdoors, test accounts, and hard-coded access paths, and why they are removed before release
- Secure defaults that fail closed when configuration is missing or ambiguous (see Module 6, section 6.4)
- Configuration review and baseline comparison as ways to detect drift from a hardened state

## 14.5 Secrets management

- What counts as a secret: passwords, API keys, tokens, private keys, and connection strings
- Why secrets must not be embedded in source code, repositories, container images, build logs, or client-side code
- Differences between environment variables, configuration files, and dedicated secret stores, and the exposure risks of each
- Why secrets are scoped to the narrowest need, and why long-lived shared credentials are avoided
- The secret lifecycle: creation, storage, access, rotation, revocation, and auditing
- Why an exposed secret is treated as compromised, rotated, and revoked, even after the commit or file is deleted
- Secret scanning and detection of secrets in repositories and build output
- How deployment-side secret handling relates to the developer's local handling of secrets (see Module 16, section 16.6)

## 14.6 Security headers in deployment

- Which response headers a deployment configures to protect browsers, and why it is set once at the server, proxy, or application level
- The purpose of HTTP Strict Transport Security (HSTS) (see Module 9, section 9.9)
- The purpose of Content Security Policy (CSP) and cookie and framing controls (see Module 4, section 4.4, and Module 9, section 9.10)
- The purpose of Cross-Origin Resource Sharing (CORS) and the risk of allowing every origin (see Module 13, section 13.6)
- Why headers are checked on every response type, including error pages and static files
- Why a report-only mode or staged rollout is used before enforcing a policy that could block legitimate behavior

## 14.7 Build and deployment pipeline security

- The pipeline as a target: source repository, build system, secrets, artifact storage, and deployment credentials
- Common attack paths: stolen pipeline credentials, malicious pull requests, modified build configuration, compromised third-party actions or plugins, and tampered artifacts
- Branch protection, required review, and signed commits as controls on what enters the pipeline
- Least privilege for pipeline identities and short-lived credentials instead of stored long-lived ones
- Separation of build, test, and deploy stages, and separation of production deployment permissions
- Pinning pipeline dependencies, such as actions, plugins, and base images, to immutable versions or digests
- Why untrusted code, such as code from forks, runs without access to secrets
- Protection of secrets used by the pipeline and masking of secrets in logs
- Software bill of materials (SBOM) as a pipeline output (see Module 10, section 10.4)

## 14.8 Container images and runtime basics

- Why containers share the host kernel and do not replace other controls
- Why containers run as a non-root user without privileged mode and with only the capabilities they need
- Why minimal base images reduce the attack surface
- Why secrets are not baked into image layers or build arguments
- Why images come from trusted sources, are pinned to a version or digest, and are rebuilt to receive updates
- Why the container runtime socket and host directories are not mounted into application containers
- Why a read-only file system and restricted network access limit what a compromised container can do
