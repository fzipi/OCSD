# Supplementary reading - Secure Configuration and Deployment

This chapter covers the security of the environment that runs an application and of the process that delivers code to it.

Secure application code is necessary but not sufficient.
An application can be well written and still be exposed by a server that publishes its source files, a service account with too many rights, a secret committed to a repository, or a pipeline that anyone can modify.
Configuration and deployment settings therefore deserve the same review as code.
[OWASP Top 10:2025 A02—Security Misconfiguration](https://top10.owasp.org/2025/A02_2025-Security_Misconfiguration/) describes how common these problems are.

## Web server and file deployment

The attack surface of a web application includes everything the server exposes, not only the code.
The web root is the directory the server publishes to clients.
Only files that clients are meant to receive belong in it.

A safe layout keeps the web root small and places everything else beside it:

```text
/app
  /public     only files meant to be served directly
  /src        application source code
  /config     configuration templates, without production secrets
  /logs       logs
  /tmp        temporary files with strict permissions
```

The server's document root points to `/app/public`, not to `/app`.
If it pointed to `/app`, a request could retrieve source code, configuration, tests, backups, or version-control data.

Files that commonly leak when they sit in a served directory include:

- Environment and configuration files such as `.env`
- Version-control directories such as `.git/`
- Backups and editor copies such as `config.php.bak`
- Test code, fixtures, and internal documentation
- Package and dependency metadata that reveals internal names or versions

Most web frameworks send every request through one entry point file.
Keeping that entry point as the only code in the web root means a server mistake does not expose application logic.

Uploaded files need a separate location outside the web root.
The application serves them after an authorization check, as described in Module 12 (section 12.7).
If uploads share a directory with static assets, a misconfigured handler can execute an uploaded file.

Related WSTG tests are [Review Old Backup and Unreferenced Files](https://wstg.owasp.org/v4.2/4-Web_Application_Security_Testing/02-Configuration_and_Deployment_Management_Testing/04-Review_Old_Backup_and_Unreferenced_Files_for_Sensitive_Information/) and [Test File Permission](https://wstg.owasp.org/v4.2/4-Web_Application_Security_Testing/02-Configuration_and_Deployment_Management_Testing/09-Test_File_Permission/).

### File permissions

File permissions decide which process can read, change, or run each file.
The aim is that a compromised process can do as little as possible.

- Application code is readable by the application and writable only by the deployment process.
- Static assets are readable by the web server.
- Only a few directories, such as upload staging and logs, are writable by the application.
- Writable directories do not allow execution, and executable files are not writable by the application.
- No file is world-writable.

If the application can overwrite its own code, an attacker who finds a file-write flaw can turn it into code execution.
Read-only code also makes unexpected changes easier to detect.

### Separate identities

A deployment usually involves several identities:

| Identity | Purpose | Expectation |
|---|---|---|
| Web server | Accept requests, serve static files, proxy | Minimal file access, no cloud administration rights |
| Application runtime | Run business logic | Only the database, storage, and secrets the application needs |
| Build | Compile, test, package | No access to production data |
| Deployment | Release approved artifacts | Cannot rewrite source history |
| Administrator | Manage the system | Separate account, protected by MFA |

Running the web server and the application as the same powerful identity, or as root, is called identity collapse.
If an attacker gains code execution, they inherit everything that identity can do.
Dedicated, unprivileged accounts with no interactive login limit the damage.
Using separate accounts for the web server and the application means a flaw in one does not automatically expose the files of the other.

The same idea applies to cloud permissions.
A single service account that can build, deploy, read production secrets, and change infrastructure makes any compromise severe and makes incident response harder.

### Test and production

Production contains the files needed to run the application and nothing else.
Test files add risk because test environments are usually protected less than production.
Examples are test accounts with known passwords, mock authentication that always succeeds, seed data, debug endpoints, and sample files.

A multi-stage build is a common way to keep test material out of production.
One stage compiles and tests the application, and the final stage copies only the build output into the runtime image.

Test environments must not hold real personal or financial data.
Use synthetic or anonymized data, as described in Module 8 (section 8.4).

## Platform-as-a-service and cloud deployment

A platform-as-a-service (PaaS) runs the web server and operating system for the application team.
Examples include Azure App Service, AWS Elastic Beanstalk, and Google App Engine.
The provider handles patching of the host and runtime.
This does not make the application secure by itself.

The shared responsibility model divides the work.
The provider secures the underlying infrastructure.
The application team secures its code, its configuration, its identities, its data, and who can reach the application.

Settings that remain with the application team include:

- Enforcing HTTPS and redirecting HTTP requests
- Authentication and access restrictions for the application and for its management portal
- Network restrictions, such as limiting which addresses can reach the application or its administration endpoints
- Disabling remote access, such as FTP or debugging ports, that is not needed
- Application settings and the secrets they hold

Managed identities let the platform give the application an identity without storing a password or key.
The application uses that identity to request access to a database or a secret store.
Platform secret stores, such as Azure Key Vault, can inject secrets into application settings as references, so that the value is not copied into configuration.
See [Azure App Service Key Vault references](https://learn.microsoft.com/en-us/azure/app-service/app-service-key-vault-references) for one example.

Deployment slots, staging sites, and preview environments run unfinished versions of the application.
They are often reachable from the internet and may use production credentials.
Treat them like production: restrict access, use separate secrets, and remove them when they are no longer needed.

Keep configuration for each environment separate and limit who can change it.
Infrastructure as code describes servers, networks, and permissions in files that are reviewed and versioned.
That makes changes reviewable and repeatable, but the files can also contain mistakes or secrets.
They need the same review and scanning as application code.
See the [OWASP Infrastructure as Code Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Infrastructure_as_Code_Security_Cheat_Sheet.html).

## Packages and signing

Deploying a package means trusting where it came from and that nobody changed it.
Risks include a tampered download, a package from a look-alike source, a modified build output, and a replaced container image.
Module 10 covers dependency selection and supply chain risks.

A digital signature lets a verifier check two things: the artifact has not changed since signing, and the signing key belongs to a particular signer.
It does not prove the code is free of vulnerabilities.
It does not prove the signer is trustworthy, and it proves nothing if the build system or signing key was compromised.

There are three common kinds of signing.

- Code or package signing covers a release artifact, such as a library, installer, or update.
- Commit signing covers a source-control commit and shows which key vouches for the change.
- Image signing covers a container image, so that a deployment can verify the image it pulls.

Signing is only useful when someone verifies.
The verifier needs the expected signer identity or public key from a trusted source, not from the same place as the artifact.
A deployment that accepts any valid signature accepts an attacker's own signature.
A failed verification stops the deployment and is investigated.

Open-source tools such as [Sigstore Cosign](https://docs.sigstore.dev/cosign/signing/overview/) sign and verify container images.
Git hosting services can mark commits as verified, as described in the [GitHub documentation on commit signature verification](https://docs.github.com/en/authentication/managing-commit-signature-verification/about-commit-signature-verification).

Lockfiles and hash pinning protect dependencies at deployment time.
A lockfile records exact versions.
Hash pinning records the expected checksum so that a changed download fails to install.
Provenance records which source and build produced an artifact.
The [SLSA framework](https://slsa.dev/) describes levels of build integrity.
See Module 10 (section 10.5) for hashes, signatures, and provenance.

## Secure defaults

Software is often shipped with defaults chosen to make first use easy.
Examples are default administrator passwords, sample applications, open management ports, verbose error pages, permissive access rules, and debug modes.
Attackers know these defaults and scan for them.

Secure defaults mean the safe behavior applies unless someone deliberately changes it.
They also fail closed.
If a setting is missing or unclear, the application runs in its restricted mode, as described in Module 6 (section 6.4).
For example, if the environment setting is not set, the application runs in production mode without stack traces.

### Removing what is not needed

Everything deployed is attack surface.
Before release, remove:

- Unused dependencies, since each one can contain vulnerabilities
- Unneeded features, modules, and server components
- Sample files, default pages, and documentation
- Development tools and test code

Debug code deserves particular attention.
Debug flags can expose stack traces, configuration, environment variables, or interactive consoles.
Examples include a framework's debug mode, a developer-only route, and verbose logging of request data.
Production builds disable these, and a check in the build or deployment can fail when a debug flag is on.
Module 6 (section 6.8) covers production and development error modes.

### Backdoors and hard-coded access

A backdoor is a hidden way to bypass normal access controls.
Developers sometimes add a test account, a master password, or a special header to make testing easier.
These shortcuts survive into production unless a review catches them.
Remove them before deployment and treat any such path found in third-party code as a security incident.

### Hardening and drift

A hardened configuration baseline lists the secure settings for each component.
Industry guides, such as the Center for Internet Security (CIS) benchmarks, provide baselines.
Comparing running systems with the baseline detects drift, which is the gradual change of settings away from the approved state.
The [OWASP ASVS V13 Configuration chapter](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x22-V13-Configuration.md) lists configuration requirements.

## Secrets management

A secret is a value that grants access: a password, API key, token, private key, or connection string.
Anyone who obtains it can act as the application.

### Where secrets must not be

Secrets must not be embedded in:

- Source code or configuration files committed to a repository
- Container image layers or build arguments, which stay readable in the image
- Build logs and error messages
- Client-side code, which every user can read

Deleting a secret from the latest commit does not remove it from the repository history, forks, or clones.
Treat any secret that reached a repository as compromised.
Rotate and revoke it, then remove it from the history if needed.

### Where secrets should be

A dedicated secret store holds secrets, controls who can read them, and records access.
The application retrieves the secret at runtime with its own identity.
Environment variables are better than source code, but they can leak through crash dumps, diagnostic pages, child processes, and container inspection.
Files with strict permissions, mounted by the platform, are another option.
Each approach has trade-offs, so the choice depends on the platform.
See the [OWASP Secrets Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html).

### Lifecycle

A secret has a lifecycle:

1. Creation, using a strong random value
2. Storage, in a protected store
3. Access, limited to the identities that need it
4. Rotation, replacing the value regularly and after any exposure
5. Revocation, disabling it when it is no longer needed or is exposed
6. Auditing, recording who accessed it

Give each secret the narrowest scope possible.
A key that can read one storage bucket is safer than one that can administer the account.
Prefer short-lived credentials, such as tokens issued on demand, over long-lived shared ones.

### Detection

Secret scanning tools search code, history, and build output for strings that look like credentials.
Open-source examples are [Gitleaks](https://github.com/gitleaks/gitleaks) and [detect-secrets](https://github.com/Yelp/detect-secrets).
Running them as a pre-commit check and again in the pipeline catches mistakes early.

Module 16 (section 16.6) covers how developers handle secrets on their own machines.
This section covers secrets in deployed systems and pipelines.

## Security headers in deployment

Several response headers instruct browsers to apply protections.
The deployment decides where they are set, for example in the web server, a reverse proxy, a content delivery network, or the application.
Pick one place for each header, so that two layers do not send conflicting values.
Module 4, Module 9, and Module 13 teach what each header does.
This section covers the deployment concerns only.

- HTTP Strict Transport Security (HSTS) tells browsers to use HTTPS only for a site.
  Module 9 (section 9.9) covers it.
  Roll it out with a short `max-age` first, and increase it once HTTPS works on every affected subdomain.
- Content Security Policy (CSP) limits where a page may load resources from.
  Module 4 (section 4.4) covers its role as defense in depth against injection, and Module 9 (section 9.10) covers the related browser controls.
- Cross-Origin Resource Sharing (CORS) controls which other origins may read responses from the application.
  Module 13 (section 13.6) covers API-specific settings.
  The risky setting is allowing every origin, or reflecting the request's origin, on responses that use credentials.
  MDN has a [CORS guide](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS).

A strict CSP can break pages that use inline scripts or third-party content.
Deploy it first in report-only mode, using the `Content-Security-Policy-Report-Only` header, review the reports, and then enforce it.
Check headers on every kind of response, including error pages, redirects, and static files, since a proxy or error handler can omit them.
The [OWASP Secure Headers Project](https://owasp.org/projects/secure-headers-project) and the [OWASP HTTP Headers Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/HTTP_Headers_Cheat_Sheet.html) list recommended headers.

## Build and deployment pipeline security

A continuous integration and continuous delivery (CI/CD) pipeline builds, tests, and releases code.
It holds credentials for production and decides what runs there.
Compromising the pipeline gives an attacker the same reach as compromising production, often with less scrutiny.

Common attack paths include:

- Stolen or leaked pipeline credentials
- A malicious pull request that changes the pipeline definition or runs with access to secrets
- A compromised third-party action, plugin, or build tool
- Tampering with an artifact between build and deployment
- Over-privileged pipeline identities that can reach unrelated systems

Controls that reduce these risks are:

- Protect the main branch, require review, and require signed commits, so no single person can push unreviewed changes.
- Restrict who can edit pipeline definitions, and review those changes like code.
- Give each pipeline job the least privilege it needs, and use separate identities for build and deploy.
- Prefer short-lived credentials issued through identity federation, such as OpenID Connect (OIDC) between the CI service and the cloud provider, over stored long-lived keys.
- Do not expose secrets to code from forks or untrusted pull requests.
- Pin third-party actions, plugins, and base images to a full commit hash or digest instead of a movable tag.
- Mask secrets in logs and keep logs access-controlled.
- Sign build artifacts and verify them before deployment.
- Require approval for deployments to production.

A tag such as `v3` can be moved to point at different code later, while a commit hash cannot.
For example, `uses: some/action@v3` follows the tag, but `uses: some/action@<full commit hash>` stays fixed.

Pipelines should also produce a software bill of materials (SBOM), an inventory of the components in a release.
Module 10 (section 10.4) covers SBOM contents, formats, and use.
For deployment, retain the SBOM for each released version so you can check later whether a newly reported vulnerability affects what is running.

References: the [OWASP CI/CD Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/CI_CD_Security_Cheat_Sheet.html), the [OWASP Top 10 CI/CD Security Risks](https://owasp.org/projects/top-10-cicd-security-risks), and [GitHub's guidance on secure use of Actions](https://docs.github.com/en/actions/reference/security/secure-use).
Module 16 covers the developer's side, including the workstation and accounts used to push code.

## Container images and runtime basics

A container packages an application with its dependencies and runs it as an isolated process.
Containers share the host's kernel.
They isolate less strongly than virtual machines, so a weak container configuration can lead to host compromise.

A foundation-level checklist covers the settings that matter most:

- Run as a non-root user.
- Do not run privileged containers, and drop capabilities the application does not need.
- Use a minimal base image so there are fewer packages to patch or abuse.
- Keep secrets out of image layers, build arguments, and environment files baked into the image.
- Pull images from trusted sources and pin them to a version or digest.
- Rebuild images regularly to pick up fixes, and scan them for known vulnerabilities.
- Do not mount the container runtime socket or sensitive host directories into application containers.
- Use a read-only file system where the application allows it, and limit network access.

Mounting the runtime socket, such as the Docker socket, lets anything in the container control the host's containers.
That is equivalent to giving it root access to the host.

See the [OWASP Docker Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Docker_Security_Cheat_Sheet.html) and Docker's [build best practices](https://docs.docker.com/build/building/best-practices/).
Orchestrators such as Kubernetes add their own settings and are outside the scope of this module.

## Worked example: reviewing a deployment

A team describes its new application deployment:

- The web server's document root is the repository root, and the app runs as root in a container.
- A `.env` file with the database password was committed so teammates can start quickly.
- The production site is built from the default branch by a pipeline that any contributor can edit.
- The pipeline pulls a third-party action by tag and uses a long-lived cloud key stored as a pipeline variable.
- Images are pushed to the registry without signing, and the staging site is open to the internet with debug mode on.

A reviewer finds these issues:

1. The document root exposes source, tests, and `.env`. Point it to a dedicated public directory (see Web server and file deployment).
2. Running as root widens the impact of any code execution. Use a non-root user (see Container images and runtime basics).
3. A committed secret is compromised. Rotate the password, revoke the old one, and move the new value to a secret store (see Secrets management).
4. An editable pipeline lets one contributor deploy anything. Protect branches, require review, and restrict pipeline edits (see Build and deployment pipeline security).
5. The action tag can be moved, and the long-lived key can be stolen. Pin the action to a commit hash and use short-lived federated credentials (see Build and deployment pipeline security).
6. Unsigned images cannot be verified. Sign images in the pipeline and verify them at deployment (see Packages and signing).
7. The staging site with debug mode on exposes internals. Restrict access and disable debug (see Secure defaults and Platform-as-a-service and cloud deployment).

Each fix addresses a different layer, and no single control would have caught all seven.
