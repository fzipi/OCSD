# Module 6 - Error Handling

This outline defines the error-handling knowledge assessed in Module 6.

## 6.1 Errors as a security concern

- Why failure paths need the same security attention as normal paths
- Errors and exceptional conditions: invalid input, unavailable dependencies, missing or unexpected data, resource limits, and implementation defects
- How attackers deliberately trigger errors to gather information or to bypass checks
- Mishandling of exceptional conditions as a risk category (OWASP Top 10:2025 A10)
- The three failings behind it: not preventing, not detecting, and not responding properly to an unusual situation
- Weaknesses that result: information disclosure, fail-open behavior, inconsistent state, resource exhaustion, and loss of availability

## 6.2 Secure exception handling

- Catching specific exceptions instead of generic ones, and the risk of catching everything
- Empty or ignored catch blocks and unchecked return values as causes of silent failure
- Handling an error where enough context exists, and letting other errors propagate to a higher layer
- Wrapping exceptions while preserving the original cause for internal diagnosis
- Releasing resources such as connections, files, and locks on every exit path
- Rolling back partial changes when a multi-step operation fails

## 6.3 Error messages and information disclosure

- Information that internal error output can reveal: stack traces, file paths, framework and version details, queries, schema names, hostnames, and secrets
- How this information supports reconnaissance and injection attacks
- Error messages that reveal whether an account, record, or permission exists
- Differences in response content, status code, or timing that reveal the same facts
- Generic user-facing messages combined with a correlation identifier for support
- Consistent response format and appropriate HTTP status codes for errors in web applications and APIs

## 6.4 Failing securely

- Fail-secure (fail-closed) and fail-open behavior
- Denying access and rejecting the operation when an authorization or validation check cannot complete
- Restrictive defaults for security decisions when data or a dependency is unavailable
- Security invariants that must hold during failures, such as "a failed check never allows the operation"
- Graceful degradation when an external dependency fails, and why security controls are not degraded to keep features working
- Fail-secure as a secure design principle owned by Module 1 (section 1.2)

## 6.5 Centralized error handling

- Why one consistent mechanism for handling errors is easier to review and test than scattered handlers
- Global exception handlers and framework error middleware
- Last-resort handlers that catch unhandled exceptions
- Languages and frameworks without exceptions that need an equivalent pattern
- Generic responses to callers from the global handler, with detail kept for internal records
- Limits, quotas, and input validation (Module 4, section 4.2) that prevent many exceptional conditions

## 6.6 Error details in logs

- Which error details belong in internal records: time, request or correlation identifier, error type, and the affected component
- Why stack traces and detailed diagnostics are recorded internally and not shown to users
- Why error records must not contain passwords, tokens, keys, or personal data
- Logging and protection of error records are covered in Module 7 (sections 7.3 and 7.4)

## 6.7 Development and production error behavior

- Detailed errors and debug features in development, and generic errors in production
- Debug mode, verbose errors, and default framework error pages as misconfigurations
- Environment-specific configuration that defaults to the secure production behavior
- Testing error paths, including responses, failure behavior, and environment separation
