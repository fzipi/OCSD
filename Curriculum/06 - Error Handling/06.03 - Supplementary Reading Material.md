# Supplementary reading - Error Handling

This reading teaches the topics in the Module 6 body of knowledge.
It is written for developers who are new to security.
Logging of errors is covered in Module 7.

## 6.1 Errors as a security concern

Applications do not run only under ideal conditions.
They receive invalid input, lose connections to databases and other services, run out of memory or disk space, and contain defects.
An error is a failure the program detects, and an exceptional condition is any unusual situation the normal code path does not expect.
Many languages report these situations as exceptions, which are signals that interrupt normal execution and travel up the call stack until some code handles them.

Error handling is a security topic because attackers choose the conditions the application sees.
An attacker can send malformed input, interrupt a multi-step request, or overload a dependency to see what the application does next.
The result of mishandling can be a leaked internal detail, a skipped check, a half-finished change, or a crashed service.

OWASP Top 10:2025 added A10, Mishandling of Exceptional Conditions, as a new category.
It describes three failings.
The application does not prevent an unusual situation, it does not detect the situation when it happens, or it does not respond to it properly.
Typical consequences are:

- Information disclosure, such as a database error shown to the user
- Fail-open behavior, where a failed check lets the operation continue
- Inconsistent state, such as money debited but never credited
- Resource exhaustion, such as a connection left open after every failed upload
- Loss of availability, such as an unhandled exception that ends the process

The category groups weaknesses such as CWE-209 (error messages that contain sensitive information) and CWE-636 (not failing securely, also called failing open).

A worked example.
A checkout service performs three steps: debit the buyer, credit the seller, and write a receipt.
If the network drops after step one and the code simply returns an error, the buyer has paid and the seller has not been credited.
An attacker who can repeat this on purpose can corrupt records or obtain goods without paying.
The secure design treats the three steps as one transaction and undoes the first step when a later step fails.

## 6.2 Secure exception handling

### Catch specific exceptions

A catch block that handles every possible exception makes the code appear safe while hiding real problems.
It also catches conditions the author never thought about, such as a bug or a permission failure, and treats them like the one expected case.
Catch the specific exception types the code knows how to handle, and let others propagate to a handler that can log them and respond consistently.

```python
# Risky: every failure, including a bug, is treated as "user not found"
try:
    user = db.get_user(user_id)
except Exception:
    return None

# Better: handle what is expected, let the rest propagate
try:
    user = db.get_user(user_id)
except UserNotFoundError:
    return None
except DatabaseConnectionError as error:
    raise ServiceUnavailableError("User service unavailable") from error
```

CWE-396 (declaring a catch for a generic exception) names the first pattern.

### Do not ignore errors

An empty catch block, or a function result that is never checked, hides a failure.
The program carries on as if the operation had worked.
That can mean a payment that was never recorded, a security event that was never noticed, or a permission change that was only half applied.
CWE-390 (detection of an error condition without action) describes the weakness.

If code catches an exception, it must do something deliberate.
It can recover, return a controlled error, clean up, or propagate the exception.
In the rare case where ignoring an error is correct, a comment should say why.

### Handle errors where there is context

Low-level code often cannot decide what a failure means.
A database layer knows a query timed out, but only the calling service knows whether to retry, return an error to the user, or deny the request.
Handle an exception at the layer that has enough context to act on it, and let it propagate otherwise.
Catching an exception only to throw it again unchanged adds nothing.
Catching it to add context, translate it, or enforce a security boundary does.

The outermost layer, such as a request handler, a message consumer, or a scheduled job, must catch what is left so that nothing escapes unhandled.

### Wrap exceptions and keep the cause

A layer can translate a low-level exception into one that fits its own vocabulary.
The new exception should keep the original as its cause, so internal diagnosis can still see it.

```python
try:
    result = db.execute(query, params)
except OperationalError as error:
    raise DataAccessError("Could not load the profile") from error
```

The caller sees a message about the profile, not about the database driver.
The internal records, but not the user, can show the full chain.

### Release resources on every path

Failures must not leave connections, file handles, locks, or temporary files in use.
Repeated failures that leak a resource let an attacker exhaust it, which is the first example attack scenario in OWASP Top 10:2025 A10.
Use the language features that guarantee cleanup: `try-with-resources` in Java, `using` in C#, `with` in Python, and `defer` in Go.
Otherwise use a `finally` block.

```java
try (Connection connection = dataSource.getConnection()) {
    // use the connection
} catch (SQLException error) {
    throw new DataAccessException("Could not load the record", error);
}
```

### Roll back partial changes

A multi-step operation must either complete or leave nothing behind.
Use a database transaction, or an equivalent compensating action, so a failure in a later step undoes earlier steps.
OWASP A10 calls this failing closed.
It notes that attempting to recover a transaction part way through often causes more problems than starting over.

## 6.3 Error messages and information disclosure

### What errors can reveal

A detailed error is useful to a developer and to an attacker.
The first phase of many attacks is reconnaissance, where the attacker collects technical details about the target.
Unhandled errors supply those details for free:

- Stack traces show class names, file paths, line numbers, and library versions
- Database errors show table names, column names, and sometimes the whole query
- Framework error pages show the product and version, and sometimes configuration values
- Messages can include hostnames, internal addresses, or fragments of secrets

An attacker can use this to select known attacks for a specific version, or to refine an injection attack against a query whose structure an error has shown.
The second example scenario in OWASP Top 10:2025 A10 describes an attacker who keeps forcing database errors for this purpose.

### Messages that confirm facts

Some messages reveal information through what they say.
A login form that answers "no such user" versus "wrong password" tells an attacker which usernames exist.
A message such as "you do not have permission to edit invoice 4711" confirms that invoice 4711 exists.
The same applies when two cases return different status codes, different response sizes, or noticeably different response times.
The OWASP Authentication Cheat Sheet recommends the same response for every login failure.
Module 5 (section 5.4) covers timing differences in more detail.

### Generic message plus correlation identifier

The usual approach is to show the user a short, generic message and to record the details internally.
The two are linked by a correlation identifier, which is a random value generated for the request.

```json
{
  "status": 500,
  "message": "Something went wrong. Please contact support and quote the reference.",
  "reference": "b3f9c1e2-5a7d-4e0b-9c64-1f2a3d5e7b90"
}
```

Support staff can search the internal records for that reference.
The user, and any attacker, learns nothing about the cause.
The identifier should be random and must not encode internal data such as a user name or a server name.

### Format and status codes

Web applications and APIs should return errors in one consistent format.
APIs commonly use HTTP status codes together with a small structured body.
RFC 9457 defines a standard "problem details" format for this.
Choose status codes that describe the class of problem without leaking more than needed, for example 400 for invalid requests, 401 or 403 for authentication or authorization failures, 404 for missing resources, and 500 for unexpected server failures.
Do not use 200 for an error response.
Do not return a raw internal exception as the body.

## 6.4 Failing securely

### Fail-secure and fail-open

A system fails secure (also called failing closed) when an error leaves it in the more restrictive state.
It fails open when an error makes it more permissive, for example by granting access, skipping a check, or processing a request anyway.
A temporary outage is usually recoverable, while a breach may not be.
For security controls, failing secure is the correct choice.
Module 1 (section 1.2) covers fail securely as a design principle.
This module covers how it appears in code.

```python
def is_authorized(user, resource):
    try:
        return policy_service.check(user, resource)
    except PolicyServiceError:
        # Fail secure: if the answer is unknown, the answer is no
        return False
```

The fail-open version returns `True` in the `except` branch "so users are not blocked".
Anyone who can make the policy service fail, even briefly, then has full access.

### Restrictive defaults

Variables that hold a security decision should start in the denied state.
An `authorized` flag should be false until a check sets it to true.
If a permission cannot be looked up, treat it as not granted.
If a session cannot be validated, treat it as invalid and require authentication again.
If input fails validation, reject the request instead of continuing with partly validated data.
OWASP ASVS 5.0.0 requirement 16.5.3 says the application should prevent fail-open conditions such as processing a transaction despite errors in validation logic.

### Security invariants

A security invariant is a rule that must always be true, such as "an unauthenticated request never reaches a protected resource" or "a transaction is fully committed or fully rolled back".
Error handling must keep these rules true during timeouts, exceptions, and partial failures.
When writing or reviewing a catch block, ask what rule the code in the `try` protects, and whether the `catch` still enforces it.

### Graceful degradation

External dependencies fail, and applications should keep working where it is safe to do so.
A recommendations service can be skipped, and a cached page can be served.
A policy service, a token validation service, or a fraud check must not be skipped, because those are security controls.
ASVS requirement 16.5.2 asks that the application continues to operate securely when an external resource fails.
A circuit breaker, which stops calling a failing dependency for a while, is one pattern used for this.
When one opens around a security control, the application must deny the operation, not allow it.

## 6.5 Centralized error handling

### One mechanism

If every function handles errors its own way, responses become inconsistent and some paths are forgotten.
A central handler gives one place to review and test.
OWASP A10 recommends handling exceptional conditions in one place, the same way each time.
Most frameworks provide the building blocks:

- Global exception handlers (for example, `@ControllerAdvice` in Spring or `UseExceptionHandler` in ASP.NET Core)
- Error-handling middleware (for example, in Express)
- Error handlers registered per exception type (for example, in Flask)
- Configurable error pages for status codes such as 404 and 500

Each of these converts an unhandled problem into a safe response and records the detail internally.
The documentation of the framework in use shows the exact mechanism.

### Last-resort handler

A last-resort handler catches any exception that nothing else handled.
It prevents two problems: losing the error details because nothing recorded them, and an unhandled error ending the whole process.
ASVS requirement 16.5.4 asks for one.
Some languages, such as Go and Swift, do not use exceptions in the usual way.
There the equivalent is a pattern such as checking returned errors consistently and using a single recovery point for panics.

### Preventing errors

The best handling is to prevent the condition.
Validating input stops many exceptions before they happen (see Module 4, section 4.2).
Limits, quotas, and timeouts on requests, uploads, and downstream calls reduce resource exhaustion.
A10 also notes that identical repeated errors can be summarized as counts to keep records manageable.

## 6.6 Error details in logs

The detail removed from user messages has to go somewhere.
Internal records for errors normally contain:

- The time of the event
- A request or correlation identifier
- The type of error and the component that raised it
- The user identifier, if the user was authenticated
- A stack trace, stored only in access-controlled records

They must not contain passwords, session tokens, API keys, cryptographic keys, payment card data, or other personal data.
Exception messages can contain such values, for example when a failing statement includes a password.
Sanitize or omit them before writing.

Module 7 teaches what security logs contain (section 7.3) and how to protect them (section 7.4).
Module 6 only asks that error handling keep user-facing detail and internal detail separate.

## 6.7 Development and production error behavior

During development, detailed errors, stack traces, and debug consoles help find defects.
In production they are a vulnerability.
CWE-209 and OWASP Top 10:2025 A02 (Security Misconfiguration) cover this case: debug features left on, default error pages shown, and verbose errors enabled.

Frameworks provide a setting, such as Django's `DEBUG`, that switches between the two behaviors.
Good practice is to:

- Choose the mode through environment-specific configuration
- Make production behavior the default if no value is set
- Check in deployment that debug features are off in production

### Testing error paths

Testing success cases is not enough.
Security testing of error handling checks that:

- Production responses contain no stack traces, paths, versions, queries, or secrets
- A failing dependency leads to denial, not access
- A failure part way through an operation leaves no partial state
- Internal records contain the diagnostic detail with sensitive values removed
- Debug mode and default error pages are off in the production configuration

The OWASP Web Security Testing Guide has test cases for improper error handling and stack traces.
