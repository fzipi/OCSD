# Supplementary reading – Business Logic Security

This chapter explains how attackers misuse the rules and workflows of an application, and how developers review features for these weaknesses.

## Business logic flaws

Business logic is the set of rules that decide what an application allows.
Examples are "an order ships only after payment", "a coupon can be used once", and "a refund cannot exceed the amount paid".
A business logic flaw is a gap in these rules.
The application does exactly what the code says, but the code does not say enough.

These flaws differ from implementation defects such as SQL injection.
Injection breaks the boundary between data and code.
A business logic flaw breaks no technical boundary.
Every request can be well-formed and use a legitimate function, yet the combination of requests gives the attacker something the designers never intended.

Typical causes are:

- A rule that exists only in the user interface and not on the server
- An assumption that users follow the intended sequence of steps
- An assumption that one request is processed at a time
- A combination of valid features that was never considered together, such as a discount code and a refund
- A boundary value that was never considered, such as a negative quantity

Generic scanners find these flaws only with difficulty.
A scanner does not know that a price should never change between the cart and the payment, or that a coupon is meant to be single-use.
People who know the rules of the application find them by reviewing designs and by testing abuse cases.

The consequences are usually financial or reputational: free goods, fraudulent refunds, stolen loyalty points, or unfair access to limited products.
Some flaws also create compliance problems, for example when an approval step required by regulation can be skipped.

A misuse case or abuse case describes how an attacker might use a feature against its purpose.
For a coupon feature, abuse cases include guessing codes, redeeming a code twice at once, and combining it with an incompatible offer.
Writing abuse cases during design (see Module 1) turns unstated assumptions into explicit rules that can be implemented and tested.

The [OWASP Business Logic Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Business_Logic_Security_Cheat_Sheet.html) and the [OWASP Top 10 for Business Logic Abuse](https://owasp.org/projects/top-10-for-business-logic-abuse) list common patterns.

## Workflow and state integrity

Many features are workflows: a checkout, a password recovery, a loan approval.
Each workflow has steps and a rule for which step may follow which.
A workflow bypass attack skips, repeats, or reorders steps.

Examples include:

- Calling the "order confirmed" endpoint directly without completing payment
- Reusing the final step of a password reset with another user's identifier
- Approving a request that the requester should not be able to approve
- Repeating a "refund" step after it already succeeded

The root cause is usually that the server trusts the client to follow the sequence.
Hidden form fields, URL parameters, or cookies that carry the "current step" can be changed.

The server should keep the workflow state itself, in a data store linked to the user's session or account.
Each request is then checked against that state: is this transition allowed from the current state?
A workflow can be described as a small state machine.
For an order, the states might be `cart`, `awaiting_payment`, `paid`, `shipped`, and `cancelled`.
Only some transitions are valid: `paid` can become `shipped`, but `cart` cannot become `shipped`.
Any other transition is rejected.

Workflow state that is referenced by a predictable identifier, such as an order number, is a risk.
An attacker who changes the number may reach another user's workflow.
The server must therefore also check that the workflow belongs to the current user, which is an authorization check (see Module 3).

Multi-step processes also need rules for the unhappy paths:

- Abandoned flows should expire, so that an old session cannot be completed days later.
- Partially completed steps should not leave the system in an inconsistent state, for example stock reserved but never released.
- Data collected in an early step should not be changed by the client in a later step without being validated again.

Cryptographically signed tokens can protect state that must travel through the client, such as a cart or a recovery link.
The signature lets the server detect changes.
The token should still expire and should be tied to the user and the purpose.
Keeping the state on the server is simpler and safer when it is possible.

## Race conditions and TOCTOU

A race condition is a flaw that depends on the timing or order of concurrent operations.
Web applications handle many requests at once, so two requests can read and change the same data at nearly the same time.

Time-of-check to time-of-use (TOCTOU) is a common form.
The code checks a condition, then acts on it, and the condition changes between the two.

Consider a coupon that can be used once:

1. Request A reads the coupon and sees that it is unused.
2. Request B reads the same coupon and also sees that it is unused.
3. Request A applies the discount and marks the coupon used.
4. Request B applies the discount and marks the coupon used.

The coupon was redeemed twice, although each request checked the rule.
Attackers can send many requests in parallel to widen the gap.
The same pattern allows spending a balance twice, withdrawing more than the account holds, or buying more stock than exists.

The following simplified code shows the flaw and a fix in which the check and the update happen in one atomic statement:

```sql
-- Flawed: check and update are separate steps
SELECT used FROM coupons WHERE code = 'SAVE10';
UPDATE coupons SET used = TRUE WHERE code = 'SAVE10';

-- Better: one atomic statement; zero rows updated means the coupon was already used
UPDATE coupons SET used = TRUE WHERE code = 'SAVE10' AND used = FALSE;
```

The application then applies the discount only when exactly one row was updated.

Common controls are:

- Atomic operations, which make the check and the change one indivisible step
- Database transactions with a suitable isolation level
- Locking, which lets only one request work on the data at a time
- Optimistic concurrency, which stores a version number and rejects an update if the version changed since it was read
- Database constraints, such as a unique constraint, which enforce the rule even if application code has a gap
- Idempotency keys, which let the server recognize a repeated request and return the earlier result instead of acting twice

Enforcing the rule in the data store matters because the application may run as many instances.
A lock held in the memory of one instance does not protect the others.

TOCTOU also appears with files, where a program checks a file and then opens it (see Module 12).
The principle is the same: avoid separate check and use steps.

## Business rule validation and value manipulation

Input validation (see Module 4) checks that data has the right form, such as a number in a range.
Business rule validation checks that an action is allowed by the business rules, such as "this customer may order at most five units".
Both must run on the server.

Client-supplied values that attackers can change include:

- Prices, totals, and currencies in hidden form fields or request bodies
- Quantities and product identifiers
- Discount amounts and shipping costs
- Role, status, or ownership fields in a JSON body

The server should calculate prices and totals itself from authoritative data, such as the product database.
It should accept only identifiers and quantities from the client.
If a value must travel through the client, the server should verify it against its own data before using it.

Boundary values deserve explicit rules:

- Negative quantities can turn a payment into a refund
- Zero values can skip a charge or a check
- Very large values can overflow a counter or a total
- Rounding and currency conversion can create small gains that add up when repeated

Cross-field and time-based rules express relationships: the end date is after the start date, the refund is at most the amount paid, the offer is valid until a deadline.

Promotions are a frequent target:

- Coupon codes that are short or sequential can be guessed
- Single-use codes can be redeemed again through a race condition
- Discounts that should not combine may be stacked in an unexpected order
- Referral and loyalty programs can be abused with fake accounts

Defenses include random, long codes, server-side tracking of each use, explicit compatibility rules, limits per account, and monitoring for unusual patterns.

Inventory has similar issues.
A "reserve" function that holds stock without limit lets an attacker block a product by reserving all of it.
Reservations need an expiry, and stock changes need atomic updates (see race conditions above).

For high-value operations, such as a large transfer, the application should make sure that the data the user approved is the data that is executed.
The [OWASP Transaction Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Transaction_Authorization_Cheat_Sheet.html) describes how to bind the approval to the transaction details.

## Anti-automation and abuse limits

Automation turns a small abuse into a large one.
Scripts can create thousands of accounts, scrape data, buy limited stock before real customers can, or test stolen passwords.
The [OWASP Automated Threats to Web Applications](https://owasp.org/projects/automated-threats-to-web-applications) project catalogs such threats.

Two kinds of limits help, and they have different purposes:

- Rate limiting restricts how many requests a client can make in a time window, which protects availability and slows brute force.
- Business-flow limits restrict how often a business function can be used, such as one coupon per customer or a maximum number of tickets per order.

Business-flow limits should be tied to something the attacker cannot easily multiply, such as a verified account or a payment method.
A limit based only on an IP address is weak, because attackers can use many addresses and legitimate users can share one.

Other controls include:

- CAPTCHA and similar challenges, which add friction for people and can be solved by services, so they slow automation but do not stop it
- Behavioral signals, such as a form completed faster than a person could
- Device signals, which can be spoofed and raise privacy concerns
- Proof-of-work challenges, which make each request cost computing time

No single control is sufficient.
The right combination depends on the value of the function and the cost to real users.

Monitoring completes the picture.
Logging failed redemptions, high request rates, and unusual combinations lets a team notice abuse and respond (see Module 7).
Rate limiting of APIs is covered in Module 13, and defenses against credential stuffing in Module 2.

## Failing securely in business processes

Failing securely means that when something goes wrong, the system ends in a safe state (see Module 1; error handling is covered in Module 6).
In a business process, this means the action is denied and no partial result remains.

Examples:

- If the check for sufficient funds cannot reach the account service, the payment is declined, not approved.
- If the authorization service times out, the request is denied.
- If a step fails after stock was reserved, the reservation is released.
- If the payment succeeds but the order cannot be saved, the system records the problem for reconciliation instead of silently losing the order.

Transactions help keep related changes together: either all succeed or none do.
When several services are involved, a transaction across them is difficult, so the design should define how a failed step is undone or reconciled.

Retries must be safe.
A client that repeats a request after a timeout should not be charged twice, which is the role of idempotency keys.

Error messages should help legitimate users without revealing the rules to an attacker.
"Coupon invalid" is better than a message that says whether the code exists, has expired, or has been used by another account.

## Testing business logic

Business logic is tested by comparing what the application should allow with what it allows.
Because the rules are specific to each application, automated scanners cannot do this alone.
Teams add their own tests.

Useful test types are:

- Abuse-case tests that try each abuse case written during design
- Boundary-value tests with zero, negative, maximum, and just-over-limit values
- Workflow tests that call steps out of order, repeat them, or skip them
- Concurrency tests that send the same request many times at once
- Authorization tests that use one user's workflow with another user's session

Manual review is valuable, particularly for new features that combine existing ones.
Automated regression tests keep a fixed flaw from returning.
The [OWASP Web Security Testing Guide](https://wstg.owasp.org/v4.2/4-Web_Application_Security_Testing/10-Business_Logic_Testing/) has a chapter with test descriptions.

## Worked example: coupon redemption in a checkout

A team adds a "WELCOME10" coupon that gives 10 percent off a customer's first order.
The review starts by writing the rules and abuse cases.

Rules:

- One use per customer
- Valid for new customers only
- Cannot be combined with other discounts
- Expires on a fixed date

Abuse cases and the controls they lead to:

- Changing the discount value in the request: the server computes the discount from its own coupon record.
- Redeeming the coupon in two parallel requests: the redemption is recorded with a conditional update and a unique constraint on customer and coupon, so the second request fails.
- Applying the coupon after payment confirmation: the order state machine allows discounts only in the `cart` state.
- Creating many accounts to reuse the coupon: the rule is tied to a verified email address and payment method, and sign-ups from one source are limited and monitored.
- Guessing coupon codes: codes are long and random, and failed attempts are limited per account.
- Failure of the pricing service: the checkout is stopped, not completed at the full or a default price without a check.

The tests then mirror these cases: a modified discount value, a parallel redemption, an out-of-order call, a repeated redemption, an expired coupon, and a simulated pricing service failure.
Each fixed abuse case stays in the regression suite.
