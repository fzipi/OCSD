# Supplementary reading – Security of and for AI

This chapter covers the security risks of applications that use large language models (LLMs), AI agents, and the Model Context Protocol (MCP).
It is written for developers who use models and services and do not train them.

The chapter follows the two parts of the body of knowledge.
Part A covers the OWASP Top 10 for LLM Applications 2026.
Part B covers agents and MCP.

The 2026 edition of the Top 10 is published as a [downloadable document on the OWASP GenAI Security Project site](https://genai.owasp.org/resource/owasp-genai-llm-top-10-2026/).
The per-risk web pages on that site still describe the 2025 edition, so check the edition and the number when you read an entry.

## The OWASP Top 10 for LLM Applications 2026

The risks are numbered as follows:

- LLM01 Prompt Injection
- LLM02 Sensitive Information Disclosure
- LLM03 Excessive Agency
- LLM04 Supply Chain
- LLM05 Data and Model Poisoning
- LLM06 Unbounded Consumption
- LLM07 Misinformation
- LLM08 Hidden Context Exposure
- LLM09 Vector and Embedding Weaknesses
- LLM10 Improper Output Handling

The numbers differ from the 2025 edition.
For example, Excessive Agency was LLM06:2025 and is now LLM03, and Improper Output Handling was LLM05:2025 and is now LLM10.
System Prompt Leakage (LLM07:2025) is now Hidden Context Exposure (LLM08), which covers more than the system prompt.
Always name the edition together with the number, such as "LLM03 in the 2026 edition".

### Two kinds of AI security

Security of AI is the work of making an application that uses a model resistant to attack.
Security for AI, in the sense of this module, is the use of AI to help build or secure software.
Output from an AI coding assistant is untrusted in the same way as output from a model inside an application, and it needs review, testing, and scanning.
This module concentrates on the first meaning.

### Why instructions and data mix

A traditional application separates code from data.
A database driver, for example, can send a query and its parameters separately.
An LLM receives instructions and data as one stream of text.
It has no reliable way to tell which part is an instruction from the developer and which is content that merely looks like one.

Many of the risks below follow from this property.
A second property is that model output is not deterministic and can be wrong.
A security control must therefore never depend on the model deciding to follow a rule.
Controls belong in ordinary code outside the model, where they behave the same way every time.

## Instructions, hidden context, and model output

### Prompt injection (LLM01)

In direct prompt injection, a user types text that changes how the model behaves.
Typical goals are to override the developer's instructions, to extract data, or to trigger an action.

In indirect prompt injection, the instructions arrive in content the application retrieves.
A web page, a document, an email, a tool result, or a stored memory can all contain text aimed at the model.
The user may never see this text, and the application owner may never have written it.

Filtering input, wrapping untrusted text in delimiters, and writing firmer system prompts all reduce the success rate of simple attacks.
None of them creates a trust boundary, because the model still reads everything as one stream.
The [OWASP LLM Prompt Injection Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html) treats input handling as necessary but not sufficient.
It pairs it with controls that limit what an injected instruction can achieve:

- Give the application only the permissions its task needs.
- Validate model output before it is used.
- Require human approval for high-risk operations.
- Limit request rates.

Design on the assumption that injection will sometimes succeed.
Ask what the worst action is that the model can cause, and remove the ability to cause it.

### Hidden context exposure (LLM08)

Hidden context is everything in the model's context that the user is not meant to see.
It includes the system prompt, developer instructions, tool schemas, retrieved policy text, and workflow rules.
Users can often make a model reveal it by asking in many different ways, and the model has no reliable way to refuse.

Treat all hidden context as discoverable.
Do not place credentials, API keys, or other secrets in a prompt.
Do not rely on the prompt to enforce a rule such as "only administrators may see this record".
Enforce such rules in code that checks the caller's identity and permissions.
Hiding or disguising the text of a prompt is not a security control.
If an attacker can read the whole prompt and still cannot do anything harmful, the design is sound.

The [OWASP Secrets Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html) applies to AI applications in the same way.

### Improper output handling (LLM10)

Model output is untrusted input to whatever consumes it.
That consumer may be a browser, a shell, a database driver, a template engine, or another service.
An attacker who can influence the model, through prompt injection or poisoned data, can often influence what the output contains.

Typical failures are the same as in other applications:

- Rendering model output as HTML or Markdown with active content, which causes cross-site scripting.
- Building a database query or a shell command from model output, which causes injection.
- Passing a model-chosen URL to a server-side request.
- Running generated code without review or isolation.

The controls are also the same.
Encode output for the place where it is used, validate it against an expected format, and pass values to interpreters as parameters.
Module 4, section 4.3, covers injection prevention, and section 4.4 covers output encoding.
The [OWASP Application Security Verification Standard 5.0.0: V1 Encoding and Sanitization](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x10-V1-Encoding-and-Sanitization.md) chapter defines requirements that apply to model output in the same way as to any other untrusted data.
The 2026 entry also covers insecure code produced by coding assistants, which needs code review and security testing like any other contribution.

## Data, retrieval, and the supply chain

### Sensitive information disclosure (LLM02)

Sensitive data can leave an LLM application through several paths:

- The model's answer.
- Prompts and retrieved content sent to an external provider.
- Logs and tool-call records.
- Embeddings stored in a vector database.
- Fine-tuning data the model has memorized.

The main defense is to send and store less.
Remove personal data and secrets before they enter a prompt, a log, or a training set, and send only the fields the task needs.
Module 8, section 8.3, covers data minimization.
Module 7, section 7.2, covers what must not be logged, and the same rule applies to prompts and responses.

### Supply chain (LLM04)

A model is a component that comes from a supplier, like a library.
Adapters, datasets, model files, and the packages that load them are supply chain components too.
Risks include tampered model files, malicious code that runs when a model file is loaded, and datasets from unknown sources.
A particular risk is invented package names: coding assistants sometimes suggest packages that do not exist, and an attacker can register such a name.

Apply the practices of Module 10: use trusted sources, verify integrity and provenance, pin versions, and review what you add.
Check that a package an assistant suggests exists, is the intended one, and passes the same selection checks as any other dependency.
[Chapter 6 of the OWASP AISVS](https://github.com/OWASP/AISVS/blob/main/1.0/en/0x10-C06-Supply-Chain.md) lists verification requirements for the AI supply chain.

### Data and model poisoning (LLM05)

Poisoning is the deliberate corruption of data the model learns from or retrieves.
It can target pre-training data, fine-tuning data, or the documents in a retrieval store.
The result can be a model that gives wrong answers on chosen topics or follows a hidden trigger.
Because the behavior is learned, it persists and is hard to find by testing.

A developer who only consumes models cannot inspect training data.
The developer can control what goes into fine-tuning sets and retrieval stores that the team owns:

- Record the source and version of each dataset.
- Accept data only from approved locations.
- Verify hashes or signatures where the publisher provides them.
- Review changes before they reach production.

[Chapter 1 of the OWASP AISVS](https://github.com/OWASP/AISVS/blob/main/1.0/en/0x10-C01-Training-Data-Integrity-and-Traceability.md) covers training data integrity and traceability.

### Vector and embedding weaknesses (LLM09)

Retrieval-augmented generation (RAG) lets an application add its own documents to a prompt.
It converts documents to numeric vectors called embeddings, stores them in a vector database, and finds the ones closest in meaning to a question.

The main weakness is access control.
A vector store often holds documents from many users or tenants.
If the search does not apply the requesting user's permissions, the model can quote a document the user may not read.
The same applies when the application searches with its own broad credentials.
Retrieved documents are also untrusted content and can carry indirect prompt injection.
Embeddings themselves can reveal information about the text they came from, so they need the same protection as the source data.

Enforce permissions at retrieval time, separate tenants, and review what is added to the store.
[Chapter 8 of the OWASP AISVS](https://github.com/OWASP/AISVS/blob/main/1.0/en/0x10-C08-Memory-Embeddings-and-Vector-Database.md) covers memory, embeddings, and vector databases.

## Reliability and resource use

### Misinformation (LLM07)

A model can produce text that is fluent, confident, and wrong.
The risk grows when people or automated steps act on the answer without checking it.
Examples are a support bot that states a refund policy that does not exist, or a pipeline that executes a command the model invented.

Reduce the effect by giving the model verified sources to answer from, showing which source an answer used, and telling users that the answer is AI-generated.
For decisions with real consequences, require a person to verify the answer.
Do not let unverified model output trigger an irreversible action.

### Unbounded consumption (LLM06)

Every model call costs money and compute.
An attacker, or a bug, can send many requests, very long inputs, or inputs that cause long outputs.
The results are service disruption and unexpected bills, an attack sometimes called denial of wallet.
Large numbers of queries can also be used to copy a model's behavior, which the entry calls model extraction.

Set limits in code:

- Maximum input and output tokens per request.
- Request rates and budgets per user, API key, and tenant.
- Timeouts and a maximum number of retries or recursive calls.
- Alerts when usage is unusual.

Require authentication for model endpoints so that limits apply to an identity.
Module 13, section 13.4, covers rate limiting.
The [OWASP AI Exchange section on threats through use](https://owaspai.org/docs/2_threats_through_use/) notes that limiting access per actor also slows the experimentation behind many attacks on models.

## Excessive agency and agent design

### From chat to agents

A chat application returns text.
An agent lets the model choose tools and take actions, such as sending an email, querying a database, changing a record, or running code.
A mistake or an injected instruction then has real effects.

Excessive agency (LLM03) has three causes:

- Excessive functionality: the agent has tools it does not need, such as a general shell when it only reads tickets.
- Excessive permissions: a tool runs with more privilege than the task needs, such as database administrator rights for a read-only lookup.
- Excessive autonomy: the agent takes high-impact actions without a person confirming them.

### Controls

Give each agent only the tools it needs, and scope each tool to the specific resources and operations the task requires.
Run tools with the identity and permissions of the requesting user or a narrow service identity, not a shared powerful account.
Module 3 covers authorization.

Enforce authorization in the component that runs the tool, not in the prompt.
The model can be persuaded to ask for anything, so the tool must check whether the request is allowed.
The [OWASP AI Agent Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/AI_Agent_Security_Cheat_Sheet.html) recommends this separation and recommends failing closed for unknown tools or missing approvals.

Require approval from a person for high-impact or irreversible actions, such as payments, deletions, and permission changes.
Show the person what will happen, with the exact parameters, and bind the approval to that action.
Log actions so they can be reviewed.
Set limits on cost, retries, and chain length so that a loop stops.
Module 7 covers logging.

## OWASP Top 10 for Agentic Applications 2026

The [OWASP Top 10 for Agentic Applications 2026](https://genai.owasp.org/resource/owasp-top-10-for-agentic-applications-for-2026/) uses identifiers ASI01 to ASI10:

- ASI01 Agent Goal Hijack
- ASI02 Tool Misuse and Exploitation
- ASI03 Identity and Privilege Abuse
- ASI04 Agentic Supply Chain Vulnerabilities
- ASI05 Unexpected Code Execution
- ASI06 Memory and Context Poisoning
- ASI07 Insecure Inter-Agent Communication
- ASI08 Cascading Failures
- ASI09 Human-Agent Trust Exploitation
- ASI10 Rogue Agents

Several map onto risks from Part A.
Goal hijack is prompt injection that changes what the agent is trying to do.
Identity and privilege abuse and tool misuse are excessive agency in practice.
Agentic supply chain vulnerabilities extend the supply chain risk to tools, plugins, and other agents.
Memory and context poisoning is poisoning of data that the agent stores and reads in later sessions.

Two points are new in the agent setting.
First, memory persists.
Content stored in one session can influence the agent in later sessions or for other users, so validate what is stored and isolate memory between users.
Second, agents can talk to other agents.
A message from another agent is untrusted input.
The receiving side must authenticate the sender and check that the sender may request the action, because a valid message is not the same as an authorized one.

Titles are sometimes shortened in secondary summaries, so use the OWASP document when exact wording matters.

## Model Context Protocol security

### What MCP is

The Model Context Protocol (MCP) is an open protocol that lets an AI application (the client) connect a model to tools and data offered by servers.
A server may be a local process or a remote service.
Each server adds tools whose names, descriptions, and schemas are given to the model, and whose results are returned to it.
See the [MCP specification](https://modelcontextprotocol.io/specification/latest) for the protocol itself.

An MCP server is therefore software that runs with the user's permissions or holds the user's credentials, and whose text is read by the model.
Both facts matter for security.

### Main risks

The [OWASP MCP Top 10](https://owasp.org/www-project-mcp-top-10) is a project listing the main risks.
It lists, among others, token mismanagement and secret exposure, privilege escalation through scope creep, tool poisoning, supply chain attacks, command injection, prompt injection through contextual payloads, insufficient authentication and authorization, missing audit and telemetry, shadow MCP servers, and context over-sharing.
The project is still under development, so treat its list as guidance that can change.

- Tool poisoning: a tool description or schema contains instructions for the model, and users rarely read it. The model follows them as if the developer wrote them.
- Changed definitions: a tool is approved and later changes its definition. Attackers can also add tools that shadow or imitate trusted ones.
- Tokens and secrets: credentials are stored in plain text configuration, shared across servers, or forwarded to other services.
- Broad permissions: a server holds broad scopes, so a compromise or injection reaches everything those scopes allow.
- Unsafe execution: a server builds shell commands or file paths from model-supplied values.
- Untrusted servers: users install unreviewed or unapproved servers, which are a supply chain risk like any other package.
- Injection through results: text returned by a tool is read as instructions by the model.

### Controls

The [OWASP MCP Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/MCP_Security_Cheat_Sheet.html) groups recommendations that include the following:

- Give each server the least privilege it needs, with separate and short-lived credentials per server.
- Review the complete tool definition, and require re-review when it changes.
- Authenticate access to remote servers and verify that a token was issued for the server that receives it.
- Run servers in a sandbox with limited file system and network access.
- Require approval from a person for destructive, financial, or data-sharing actions, and show the full parameters.
- Validate input and output of tools, and treat tool results as untrusted.
- Install servers only from trusted sources, and review them like any other dependency.
- Log tool calls for audit.

[MCP security best practices](https://modelcontextprotocol.io/docs/tutorials/security/security_best_practices) from the protocol's maintainers cover the same ground from the protocol side.

## Worked example

A team adds an assistant to a customer portal.
It answers questions from a knowledge base of support documents and can create a support ticket for the signed-in customer.

The team reviews the design against the Top 10:

- Hidden context (LLM08): the system prompt contains a rule that customers may only see their own tickets and an API key for the ticket service. The team assumes the prompt can be read. It moves the key to a secrets store used by the ticket tool and removes the rule from the prompt.
- Authorization (LLM03): the ticket tool runs with a shared service account that can read every ticket. The team changes it to call the ticket service with the signed-in customer's identity, so the service itself enforces ownership. The tool can create tickets and read the customer's own tickets, and nothing else.
- Retrieval (LLM09): the knowledge base mixes public articles and internal notes. The team adds an access label to each document and filters on it at search time.
- Indirect injection (LLM01): customers can upload files that are indexed. The team treats retrieved text as untrusted and keeps the assistant from having any tool that sends data to external addresses.
- Output (LLM10): the portal rendered the answer as HTML. The team renders it as text and encodes it for the page, and it validates ticket fields against the ticket service schema.
- Consumption (LLM06): the team sets a maximum input size, a per-customer request rate and daily token budget, and an alert for unusual usage.
- Misinformation (LLM07): answers show the source article, and the assistant refers refund decisions to a person.
- Approval (excessive autonomy): creating a ticket is low risk and runs directly. Closing a ticket or issuing a credit is not offered to the assistant at all.

After the review, a successful injection can at worst make the assistant create a ticket with odd text for that one customer.
