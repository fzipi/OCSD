# Supplementary reading – Secure File and Resource Handling

This chapter explains how files and user-supplied addresses become security risks, and how developers handle them safely.

## File upload risks and validation

A file upload feature lets an outside party place data on the server.
Uploaded files can carry malicious content, such as a script or an executable.
They can also be very large, or look harmless but behave differently than expected.
If the server stores the file in a place where it is executed or served unsafely, the upload becomes a way to attack the server or its users.

The main risks are:

- Code execution, when an uploaded script is placed where the web server runs it
- Stored attacks on other users, when an uploaded HTML or SVG file runs script in a browser
- Denial of service, through very large files or many files
- Exposure of data, when files are stored where others can read them

No single check is enough, so uploads are validated in layers.

Extension check.
Compare the file extension with an allowlist of permitted types, such as `.png`, `.jpg`, and `.pdf`.
Reject everything else.
An allowlist works better than a list of forbidden extensions, which always misses some entries.
Take care with double extensions such as `report.pdf.php` and with case variations.
Evaluate the final extension after the name has been normalized.

Content-Type header.
The `Content-Type` of an upload request is set by the client.
An attacker can send any value.
The header can be compared with the extension to catch mistakes, but it must never be the only evidence that a file is safe.

File content.
Most formats begin with a known byte sequence, the file signature or magic bytes.
For example, a PNG image starts with the bytes `89 50 4E 47`.
Checking the signature shows what the content really is, regardless of the name.
A signature check does not prove the file is harmless.
A file can have a valid image header and carry other data after it.
Re-processing images, for example by re-encoding them with an image library, removes embedded content that the library does not preserve.

Consistency.
The extension, the declared type, and the detected content should agree.
A mismatch is a reason to reject the file.

Size limits.
Set a maximum file size, a maximum request size, and a storage quota per user.
Enforce them as early as possible, ideally at the web server or gateway, so that the application does not read an oversized body first.

File names.
The name supplied by the client is untrusted.
It can contain path separators, special characters, or very long values (see the path traversal section).
A safer approach is to generate a new name on the server, such as a random identifier, and keep the original name only as metadata after sanitizing it.

Malware scanning of uploads is a specialized control that some organizations add.
It does not replace the checks above.

The [OWASP File Upload Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html) lists the controls in more detail.

## Content type handling and sniffing

Every response that serves a file includes a `Content-Type` header.
It tells the browser how to handle the content, for example as an image or as HTML.
The server should set this header based on its own knowledge of the file, not on what the uploader claimed.

Content sniffing is a browser behavior.
When the declared type is missing or looks wrong, some browsers inspect the content and guess a type.
An attacker can exploit this: a file served as plain text or an image may be treated as HTML and run script.

The `X-Content-Type-Options: nosniff` response header tells the browser to use the declared type and not guess.
It should be sent on responses that serve uploaded or generated files.
The [MDN documentation for X-Content-Type-Options](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/X-Content-Type-Options) describes the header.

Some file types are active content even when the type is declared correctly.
HTML files can run script.
SVG images can contain script.
If the application serves such files from its own origin, the script can read the user's session data and act as the user.
Applications that must let users upload them can serve user content from a separate domain, so that the script has no access to the main application's cookies and data.
Alternatively, the application can refuse these types or force them to download.

## Path traversal and file inclusion

Path traversal happens when user input is used to build a file path, and the input can move the path outside the intended directory.
The classic example is the sequence `../`, which means "go up one directory".

Suppose a download feature reads `/var/app/files/` plus a file name from the request.
A request for `../../etc/passwd` produces `/var/app/files/../../etc/passwd`, which refers to `/etc/passwd`.
The attacker reads a file the feature was never meant to expose.

Variations include:

- Absolute paths, such as `/etc/passwd`, where the application does not expect them
- Encoded sequences, such as `%2e%2e%2f`, which a later component may decode
- Backslashes on Windows systems
- Null bytes or other special characters in older platforms that cut off the rest of the name

Defenses, from strongest to weakest:

1. Avoid user input in file paths.
   Store files under identifiers and map an identifier to a path in a database.
   The user supplies `file=4821`, not a name.
   This is called an indirect reference.
2. If a path must be built from input, canonicalize it.
   Canonicalization resolves a path to its final absolute form, removing `..` segments and following links.
   Then check that the result still begins with the intended base directory.
3. Validate input against an allowlist of permitted characters or names.
4. Run the application with an account that can read only the directories it needs.

Sanitizing a file name by removing `../` is weak.
An input such as `....//` becomes `../` after one removal.
Check the resolved path, not the input text.

The following example in Python shows the check on the resolved path:

```python
from pathlib import Path

BASE = Path("/var/app/files").resolve()

def open_user_file(name):
    path = (BASE / name).resolve()
    if not path.is_relative_to(BASE):
        raise PermissionError("Path is outside the base directory")
    return open(path, "rb")
```

File inclusion is a related problem.
Some languages and frameworks can load and run a file chosen at runtime, for example when a page parameter selects a template.
If the parameter is user-controlled, an attacker can choose a different file.
Local file inclusion (LFI) loads a file that is already on the server.
Remote file inclusion (RFI) loads a file from another server, which lets the attacker run their own code.
The safest design avoids dynamic includes based on user input.
Where it is needed, the application maps the input to a fixed list of allowed files, and remote includes are disabled in the platform configuration.

The [OWASP Path Traversal page](https://community.owasp.org/attacks/Path_Traversal) gives more examples.

## Archive extraction

Applications often accept archives, such as ZIP files, and extract them.
Each entry in an archive has a path.
An entry can be named `../../outside.txt`.
If the extraction code joins the entry name to the target directory without checking, the file is written outside the target directory.
This weakness is called Zip Slip.
It can overwrite application files, configuration, or scripts, and it can lead to code execution.

An archive can also contain symbolic links that point outside the target directory.
A later entry written through the link lands in the linked location.

Extraction should:

- Resolve the final path of every entry and check that it lies inside the target directory, as in the path traversal example
- Skip or reject symbolic links and special files
- Extract into a new, isolated directory
- Limit the number of entries and the total uncompressed size

The size limits address decompression bombs.
A small archive can expand to a very large amount of data and fill the disk or memory.
The limits should apply to the uncompressed size, which is counted while extracting, because the size declared in the archive can be wrong.

Many libraries now check paths themselves, but developers should confirm this behavior for the library they use.
The [Snyk Zip Slip research](https://security.snyk.io/research/zip-slip-vulnerability) documents the vulnerability and affected libraries.

## File storage

Where and how files are stored determines who can read them and whether they can run.

Local storage guidelines:

- Store uploaded files outside the web root, so that the web server does not serve them by path.
  The application then serves them through code that checks authorization.
- If files must be inside a served directory, disable script execution there and disable directory listing.
- Use unpredictable file names, such as random identifiers, so that names cannot be guessed.
  Unpredictable names are not access control, so authorization checks are still needed.
- Give the application account only the permissions it needs, and keep files of different sensitivity in separate locations.
- Encrypt sensitive files at rest and log access to them (see Module 8).

Cloud object storage, such as an S3-compatible service, changes the model.
Buckets should be private by default.
Public access should be an explicit, reviewed decision, because misconfigured public buckets are a common source of data leaks.

Pre-signed URLs let a client access a private object directly without passing the file through the application.
The application signs a URL with its own credentials, and the URL allows one operation on one object for a limited time.

- A pre-signed download URL lets a user fetch a file for a few minutes.
  The application checks that the user is authorized before it creates the URL.
- A pre-signed upload URL or a pre-signed POST form lets a client send a file straight to storage.
  A pre-signed POST can also state conditions, such as a maximum file size and an allowed content type, which the storage service enforces.

Expiry should be short.
Anyone who holds the URL can use it until it expires, so URLs should not be written to logs or shared.
Files uploaded directly to storage are still untrusted.
The application should validate them, for example by checking the content before it marks the file as accepted.
The [AWS documentation on pre-signed URLs](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html) and [pre-signed POST forms](https://docs.aws.amazon.com/AmazonS3/latest/API/sigv4-HTTPPOSTForms.html) show one implementation.
Other providers offer similar features.

## File download

When the application serves a stored file, it should check authorization first.
A user should only receive files they are allowed to see (see Module 3).
A common flaw is a download endpoint that takes a file identifier and does not check ownership.

Response headers control how the browser treats the file:

- `Content-Disposition: attachment; filename="report.pdf"` tells the browser to download the file and not display it.
  This avoids running active content in the application's origin.
  The [MDN documentation for Content-Disposition](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Disposition) describes the header.
- `Content-Type` should match the file.
- `X-Content-Type-Options: nosniff` stops the browser from guessing the type.
- `Cache-Control: no-store` or a private caching directive keeps sensitive files out of shared caches.

File names placed in headers must be sanitized.
A name that contains a line break could inject extra headers into the response.
Most frameworks encode the name correctly, so use their file response functions where available.

Download links can also have an expiry, as with pre-signed URLs, and the application can limit how often a file is downloaded.
Logging downloads of sensitive files supports investigation (see Module 7).

## Temporary files

Applications create temporary files for uploads in progress, report generation, and conversion.
Temporary files cause problems when they are easy to guess or readable by others.

- Predictable names let an attacker create a link or file with the same name first.
  The application then writes into a location the attacker chose.
- A shared directory such as `/tmp` is writable by all users on the system.
- Permissive file permissions allow other accounts to read sensitive data.
- Files that are never deleted accumulate and may expose data later.

Guidelines:

- Use the platform's secure functions to create temporary files, which pick unpredictable names and create the file exclusively, failing if it already exists.
  An example is the Python [tempfile module](https://docs.python.org/3/library/tempfile.html).
- Set restrictive permissions, so only the application account can read the file.
- Delete the file when it is no longer needed, including when an error occurs, for example with a `finally` block or a context manager.
- Avoid separate steps that check whether a file exists and then create it, because the state can change between the two steps.
  This is a time-of-check to time-of-use race (see Module 11).

The [OWASP Insecure Temporary File page](https://community.owasp.org/vulnerabilities/Insecure_Temporary_File) describes the issue.

## Server-side request forgery (SSRF)

Server-side request forgery occurs when an attacker can make the server send a request to a location the attacker chooses.
The request comes from the server, so it carries the server's network position and privileges.
It can reach systems that the attacker cannot reach directly.

SSRF appears in features that fetch a user-supplied address:

- Import a document or image from a URL
- Generate a link preview or thumbnail
- Fetch a profile picture from a web address
- Send a webhook to a URL the user configures
- Integrate with a remote service whose address is a parameter

Typical targets are:

- Internal services that have no authentication because they are assumed to be private, such as admin interfaces
- Loopback addresses, such as `localhost` or `127.0.0.1`, which reach services on the server itself
- Cloud metadata endpoints, such as `http://169.254.169.254/`, which can return credentials for the server's cloud role
- Other internal systems, which an attacker may map through differences in response or timing

SSRF is in the OWASP Top 10:2025 under A01 – Broken Access Control, and in API Security Top 10:2023 as API7.
This module is the main place where the topic is taught, and Module 13 refers to it for APIs.

Defenses work in layers:

1. Prefer not to accept a full URL from the user.
   If the feature needs a limited set of destinations, let the user choose from a list, and have the server look up the address.
2. If a URL is needed, allow only expected hosts, protocols, and ports.
   Accept `https` and, if required, `http`.
   Reject others such as `file`, `gopher`, and `ftp`.
   An allowlist of permitted hosts is much stronger than a denylist of forbidden ones.
3. Do not rely on denylists of internal addresses alone.
   Attackers use alternate representations of the same address, such as decimal, octal, or IPv6 forms, and host names that resolve to internal addresses.
4. Resolve the host name and validate the resulting IP address against the rules, then connect to that validated address.
   If the application validates one DNS answer and the library resolves the name again, an attacker-controlled DNS server can return a different, internal address the second time.
   This is DNS rebinding.
5. Do not follow redirects blindly.
   A permitted server can answer with a redirect to an internal address.
   Disable redirects, or validate every target.
6. Limit response size and time, and do not return the raw response to the user.
   Returning the content turns the flaw into a way to read internal data, and detailed errors help the attacker map the network.
7. Add network controls.
   Egress filtering on the server limits where it can connect.
   Cloud platforms offer options that harden metadata access, such as requiring a session token for the metadata service.
   Running the fetching component in a separate network segment limits the damage.

Applications that call out to many external locations, such as webhook senders, often put the fetching component behind a dedicated proxy that enforces these rules.

The [OWASP Server-Side Request Forgery Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html) describes these controls in detail.

## Worked example: profile picture upload and import

A team adds profile pictures.
Users can upload a file or paste a link to an image.
The review follows the path of the data.

Upload from the user's device:

- The server accepts only `.png`, `.jpg`, and `.webp`, with a maximum size of 2 MB, enforced at the gateway.
- It checks the file signature, re-encodes the image with an image library, and discards the original.
- It stores the result under a random identifier, outside the web root or in a private bucket.
- Serving the picture uses the correct `Content-Type` and `X-Content-Type-Options: nosniff`.
- The original file name is never used in a path.

Upload to cloud storage:

- The application creates a pre-signed POST that expires in five minutes and allows only images up to 2 MB.
- After the upload, the application validates the content before it marks the picture as active.

Import from a link:

- The feature is a server-side request, so the team treats it as SSRF-prone.
- It accepts only `https` links and resolves the host name.
- It rejects any resolved address in private, loopback, or link-local ranges, including the cloud metadata address, and connects to the validated address.
- It disables redirects, limits the download to 2 MB and ten seconds, and passes the result through the same validation as an uploaded file.
- If the link fails any check, the user sees a generic error.

Download:

- The profile picture URL is public by design, but the serving code never reads a path taken from the request.
- If a user's data export includes pictures, the export checks authorization first and serves the file with `Content-Disposition: attachment`.

Tests include a file with a script and a `.png` name, a file with a mismatched type, a path containing `../`, an archive with a traversal entry if archives are accepted, a link to `http://127.0.0.1`, a link that redirects to an internal address, and an oversized file.
