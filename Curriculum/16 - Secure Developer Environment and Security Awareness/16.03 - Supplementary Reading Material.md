# Supplementary reading - Secure Developer Environment and Security Awareness

This chapter covers the security of the machines, tools, and accounts developers use, and the habits that keep them safe.

Most of this curriculum protects the application.
This module protects the people and systems that build it.
An attacker who controls a developer's machine or account can read source code, steal credentials, and change what is shipped, without attacking the application at all.

## Context and threat model

### Why developers are targeted

A developer workstation brings together source code, production credentials, cloud access, package registry tokens, and access to the build pipeline.
Developers also need flexibility to install tools and run code, so their machines tend to have fewer restrictions than a typical office computer.
A compromised developer machine can bypass perimeter defenses because it already has trusted access.

Attackers may want to:

- Steal source code or intellectual property
- Obtain cloud credentials, API keys, SSH keys, or tokens
- Modify source code, dependencies, or the build pipeline
- Reach internal systems through VPN, SSH, SSO, or browser sessions
- Collect sensitive data used for testing or debugging

The 2020 SolarWinds incident is a well-known example.
Attackers compromised the build environment of a software vendor and added malicious code to updates that the vendor then distributed to its customers.
The entry point was the development and build environment, not a customer-facing server.
MITRE ATT&CK describes this class of attack as [supply chain compromise](https://attack.mitre.org/techniques/T1195/).

### Assets and threats

Assets worth protecting are:

- Source code and internal repositories
- Build artifacts and deployment configuration
- API tokens, passwords, SSH keys, certificates, and private keys
- Cloud profiles and cluster configuration files
- Database dumps, sample data, logs, and debugging output
- Browser sessions and single sign-on cookies
- Architecture diagrams, tickets, and incident details

Typical threats include:

| Threat | Example |
|---|---|
| Credential theft | A cloud key in a local `.env` file is exposed by malware or an accidental commit |
| Malicious package | A package's install script reads environment variables and SSH keys |
| Compromised extension | A hijacked editor extension sends workspace files to an outside server |
| Unsafe online tool | A developer pastes customer records into a free formatter or converter |
| Insecure remote work | A session is intercepted on an untrusted network |
| Unsafe local container | A privileged container reads host files and credentials |
| Insider or accident | A person leaks code intentionally or by mistake |

## Core principles for secure workstations

Six principles guide everyday decisions.

**Least privilege.**
Use only the access the task needs.
Work with a standard user account and elevate only when needed.
Never run the browser, email client, or IDE as root or administrator.
Any process started with elevated rights, including a malicious one, inherits them.
Prefer short-lived tokens over long-lived ones.

**Separation of environments.**
Keep development, test, staging, and production credentials and access separate.
Do not turn a workstation into an informal production console.
Use separate browser profiles, or separate devices, for work and personal accounts.

**Defense in depth.**
No single control is enough.
Disk encryption, endpoint protection, patching, MFA, and secret scanning each cover failures of the others.
Do not rely only on the corporate firewall or VPN.

**Secure defaults and updates.**
Controls that are on by default do not depend on memory.
Enable automatic updates, because many successful attacks use vulnerabilities that already have fixes.
Remove software that is not needed, since each tool adds attack surface.

**Minimize local sensitive data.**
The safest local secret or dataset is one that is not there.
Avoid downloading production data or keeping long-lived secrets.
When local sensitive data is unavoidable, encrypt it, limit how long it stays, and delete it after use.

**Verify before trusting.**
Treat each binary, script, extension, image, package, and online service as needing a trust decision.
Ask who published it, whether it is maintained, which permissions it asks for, and whether an approved alternative exists.

Baseline workstation controls are:

| Control | Purpose |
|---|---|
| Full-disk encryption | Protects data if the device is lost or stolen |
| Screen lock after a short period of inactivity | Prevents use by someone with physical access |
| Endpoint protection | Detects malware and suspicious behavior |
| Host firewall | Limits inbound connections |
| Automatic updates | Reduces exposure to known vulnerabilities |
| Removal of unneeded software | Reduces attack surface |

## Policies, roles, and responsibilities

Security policies record decisions an organization has made about acceptable risk.
Understanding their intent helps developers follow them and raise concerns when a rule does not fit the work.
Security is shared.
Developers, engineering managers, security teams, and IT or endpoint management each have a role.

Developers are generally responsible for:

- Protecting credentials, tokens, keys, and sensitive data
- Using approved tools and services
- Keeping devices patched, including personal devices when policy allows their use
- Reviewing plugins, dependencies, scripts, and containers before use
- Reporting incidents and concerns

Managers set expectations and make time for security work.
Security teams provide guidance, tools, and incident response.
IT or endpoint management runs device management, patching, and access.

Policies that developers commonly meet cover:

- Acceptable use of company devices
- Bring-your-own-device rules
- Software installation and approved IDEs, plugins, and package managers
- Cloud service and AI tool use
- Secrets management
- Production access, which is usually time-limited and logged rather than standing
- Data classification and handling, which decides whether classified data may appear in logs, test data, or local environments (see Module 8, section 8.1)
- Remote work
- Incident reporting

### Reporting

Report promptly when:

- A laptop, phone, hardware token, or storage device is lost or stolen
- A secret may have been committed, logged, shared, or exposed
- A suspicious extension, dependency, script, or binary was installed
- Endpoint protection flags a problem
- Unexpected logins, MFA prompts, or cloud activity appear
- Sensitive data was pasted into an external service

Fast reporting lets the security team rotate credentials, revoke sessions, isolate devices, and investigate.
A report without blame encourages people to speak up early.

## Use of local tools, IDEs, and plugins

An IDE reads files, runs commands, and talks to the network, so it is a high-value target.

### Extensions and plugins

Extensions run with the user's permissions.
Risks include excessive permissions, an unknown publisher, a legitimate extension sold or hijacked and then updated with malicious code, and typosquatted extension names.
Install extensions from trusted publishers, keep the list short, review requested permissions, and remove those you no longer use.

### Opening untrusted projects

Opening a project can run code.
Language servers, task runners, build tools, linters, and debug configurations may execute scripts that come with the repository.
Editors offer a restricted mode, such as VS Code's [Workspace Trust](https://code.visualstudio.com/docs/editing/workspaces/workspace-trust), which limits automatic code execution until you trust the folder.
Treat repositories from unknown sources as untrusted until you have looked at them.

### Command-line tools, Git hooks, and package managers

Shell scripts copied from the internet, especially "pipe to shell" installers, run with your full privileges.
Read a script before running it, and prefer official package sources.

Git hooks are scripts that run at points such as commit and push.
A repository can ship hook configuration that runs code on your machine, so read it before enabling it.
See the [Git documentation on hooks](https://git-scm.com/book/en/v2/Customizing-Git-Git-Hooks).

Package managers can run install scripts that read environment variables and files.
Use lockfiles and pinned versions, review new dependencies, and disable install scripts where the ecosystem allows it.
Module 10 (section 10.3) covers dependency management.
The [OWASP NPM Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/NPM_Security_Cheat_Sheet.html) lists controls for one ecosystem.

## Use of online services and free tools

Online formatters, JSON viewers, code converters, paste sites, screenshot tools, and debugging services are convenient.
Many are free because the operator collects, retains, or reuses submitted content.
Even a well-meant tool may log what you send or serve third-party scripts.

Do not submit the following to an unapproved service:

- Proprietary source code
- Passwords, API keys, tokens, private keys, and session cookies
- Customer or employee data and other regulated data
- Production logs and stack traces that contain any of the above
- Internal architecture details

Review risk factors before use: who operates the service, how long it keeps data, whether it shares or trains on it, and whether it works offline.
Safer alternatives include approved internal tools, tools that run locally, and sanitized or synthetic sample data.

### AI coding assistants

AI coding assistants send code and context to a remote service.
Follow the organization's policy on which assistants and which data are allowed.
Do not paste secrets or sensitive data.
Treat suggested code, dependencies, and commands as unreviewed input and check them as you would code from an unknown contributor.
The [OWASP Top 10 for Large Language Model Applications](https://owasp.org/projects/top-10-for-large-language-model-applications) describes related risks.

A simple check before using any online tool with work data:

1. Does the organization's policy permit it?
2. Does the provider's terms allow it to retain, analyze, or share the input?
3. Would a disclosure of this input be acceptable?
4. Is there an approved alternative?

If any answer is unclear, do not submit the data.

## Secrets management and sensitive data handling

A secret is a credential that grants access: a password, API key, token, private key, or session cookie.
Sensitive data also includes production data, personal data, and internal documents that appear in tests, logs, or screenshots.

### Principles

- Never hard-code secrets in source code.
- Do not commit secrets, even to a private repository.
  Repositories are cloned, forked, and shared.
- Prefer short-lived and narrowly scoped credentials to long-lived, powerful ones.
- Use an approved secret store or the platform's secret mechanism, not chat messages, tickets, or documents.
- Rotate and revoke a credential as soon as it may have been exposed.

Removing a secret in a later commit does not remove it from history, forks, or clones.
Treat it as compromised and rotate it.

### Local `.env` files and history

Local `.env` files are convenient and risky.
Keep them out of version control with `.gitignore`, give them restrictive file permissions, and avoid production values in them.
Secrets also appear in shell history, build logs, crash reports, and copied terminal output.

### Detection

Secret detection tools scan code and history for credentials.
Examples are [Gitleaks](https://github.com/gitleaks/gitleaks) and [detect-secrets](https://github.com/Yelp/detect-secrets).
Running them as a pre-commit check catches secrets before they leave the machine.
Hosted services can also block pushes that contain secrets, such as [GitHub push protection](https://docs.github.com/en/code-security/concepts/secret-security/push-protection).
Pre-commit hooks can be skipped, so also scan on the server side.

### Test data and logs

Use synthetic or anonymized data for development and testing, as described in Module 8 (section 8.4).
Do not copy production databases to laptops.
Before sharing logs, screenshots, or debug output, remove tokens, personal data, and internal host names.
Module 7 (section 7.2) lists what should not be logged at all.

The [OWASP Secrets Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html) covers storage and lifecycle.
Module 14 (section 14.5) covers how secrets are delivered to deployed applications and pipelines.
This module covers the developer side: the laptop, the repository, and the tools around them.

## Network, remote access, and home office

Developers work from offices, homes, and public places, and each has different risks.

### Home and public networks

Home networks are often unmanaged.
Change default router credentials, keep router firmware updated, use WPA2 or WPA3 encryption, and keep work devices on a separate network from smart home and guest devices where possible.
Public Wi-Fi allows others on the network to observe or tamper with unprotected traffic.
HTTPS protects the content of web traffic, but a user can still be tricked into joining a fake network or ignoring a certificate warning.
Use a VPN or other approved protected access for internal resources, and never click through certificate warnings.
[NIST SP 800-46 Rev. 2](https://csrc.nist.gov/pubs/sp/800/46/r2/final) gives guidance on remote access and telework security.

### Remote access

Use the access methods the organization approves, such as VPN, zero-trust access gateways, or bastion hosts.
Do not set up your own tunnels or expose internal services to the internet to make remote work easier.
Unapproved tunnels bypass monitoring and may be open to anyone.

### SSH keys

SSH keys give direct access to servers and repositories.
Protect private keys with a passphrase, use modern key types such as Ed25519, and use an agent so the passphrase is not typed repeatedly.
Use separate keys for separate purposes, never copy private keys to shared locations, and remove keys that are no longer needed.
Mozilla publishes [OpenSSH guidelines](https://infosec.mozilla.org/guidelines/openssh).

### Local development services

Development servers, databases, admin dashboards, and debug interfaces often run with weak settings.
They may use default credentials, disable authentication, and listen on all network interfaces.
On a shared or public network, anyone can reach them.

- Bind services to `localhost` unless remote access is required.
- Do not use default or production credentials.
- Stop services when finished.
- Use a firewall rule or tunnel instead of exposing a port to the internet.
- Never point a development service at production data.

### Physical security

Lock the screen when you step away.
Do not leave devices unattended in public places or vehicles.
Use a privacy screen when working in public.
Keep work conversations and documents out of view of others.

## Containerized and virtual development environments

Containers, virtual machines, development containers, and cloud workspaces create repeatable, disposable environments.
They can keep project dependencies away from the host and make setup consistent.
The [Dev Containers specification](https://containers.dev/) defines one common format.

Their security benefit depends on configuration.
Containers share the host kernel, so they isolate less than virtual machines.
Cloud workspaces move the code and its credentials to a provider, which changes who must be trusted.

Unsafe configurations include:

- Privileged containers, which remove most isolation from the host
- Mounting the container runtime socket (for example `/var/run/docker.sock`), which lets the container control other containers and often the host
- Mounting a whole home directory, which exposes SSH keys, cloud credentials, and browser data
- Running as root inside the container
- Passing host credentials or tokens into a container that does not need them
- Pulling untrusted or unpinned images

Safer practice mounts only the directories needed, runs as a non-root user, uses images from trusted sources, and scans images for known vulnerabilities.
See the [OWASP Docker Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Docker_Security_Cheat_Sheet.html) and Docker's [security documentation](https://docs.docker.com/engine/security/).
Module 14 (section 14.8) covers container settings in deployment.

## Developer awareness and secure habits

### Social engineering aimed at developers

Developers receive messages that look like normal work:

- A recruiter sends a coding test that must be cloned and run
- A pull request or issue links to a malicious repository or script
- A "fix" instructs you to paste a command into a terminal
- A message claiming to be from IT, a vendor, or a colleague asks for a token or an MFA code
- A package or extension with a name close to a popular one

The common step is that something asks you to run, install, or reveal something.
Verify the source through a second channel, read before running, and do not enter credentials on pages reached through unexpected links.
Module 10 (section 10.1) describes typosquatting and related supply chain attacks.

### Everyday habits

- Lock unattended devices.
- Use MFA on code hosting, cloud, package registry, and email accounts.
  Module 2 (section 2.3) covers MFA.
- Read commands and scripts before running them.
- Review `git diff` before committing, to catch debug code, secrets, and unintended files.
- Review code changes from others for security issues, since code review is a security control.
- Keep work and personal activities separate.
- Keep tools and dependencies updated.

### Recognizing and responding to a compromise

Signs include:

- Logins, MFA prompts, or API calls you did not make
- New SSH keys, tokens, repository collaborators, or commits you do not recognize
- Endpoint protection alerts
- Unexplained processes, network connections, or slow performance
- Notices that a credential of yours appeared in a leak or a public repository

Respond as follows:

1. Stop the suspicious activity.
  Disconnect the device from the network if malware is suspected.
2. Preserve information.
  Keep the suspicious file, message, or log instead of deleting it.
3. Revoke or rotate exposed credentials, tokens, and sessions from a clean device.
4. Report through the organization's incident-response process.
5. Follow the security team's instructions before restoring the device.

### Staying informed

Developers should know where to look for security information that affects their languages, frameworks, and tools.
Sources include the advisories of the package ecosystem and framework projects, vendor security bulletins, organizational guidance, and OWASP resources such as the [OWASP Top 10](https://top10.owasp.org/) and the [OWASP Developer Guide](https://owasp.org/projects/developer-guide).
Organizations may also provide security training, such as [SANS security awareness training](https://www.sans.org/for-organizations/workforce/security-awareness-training).

## Reviewing a developer-environment scenario

A review looks for insecure practices, excessive exposure, and missing controls, and proposes fixes that keep the team productive.
Order findings by likely impact, since exposed production credentials matter more than a missing screen lock.
Some fixes need a policy decision or specialist help instead of a developer change.

### Worked example

A developer describes their setup:

- They work from a personal laptop with no disk encryption and sign in as administrator.
- A `.env` file with production database credentials sits in the project folder, and `.gitignore` does not list it.
- They installed a theme extension from an unknown publisher, and opened a repository from a recruiter's coding test without Workspace Trust.
- They paste stack traces with customer email addresses into a free online formatter.
- They run a database in a container with port 5432 published on all interfaces, and the container mounts their home directory.
- They work from a cafe on public Wi-Fi without a VPN.

A reviewer finds these issues, in order of impact:

1. Production credentials in `.env` that are not ignored may be committed.
  Remove production credentials from the laptop, add the file to `.gitignore`, and rotate the credentials if they were ever committed or copied.
2. The home-directory mount exposes SSH keys and cloud profiles to the container.
  Mount only the project directory.
3. The published database port is reachable from the cafe network.
  Bind it to `localhost`.
4. The recruiter's repository was opened without restrictions.
  Treat it as untrusted code and use a disposable virtual machine, or restricted mode, to look at it.
5. The unknown extension can read workspace files.
  Remove it and install from trusted publishers.
6. Customer data goes to an unapproved service.
  Stop, report it as a possible data exposure, and use sanitized samples.
7. A personal, unencrypted laptop breaks the baseline.
  Use an approved managed device or enable encryption and a standard account.
8. Public Wi-Fi without protection adds exposure.
  Use the approved VPN.

Each finding maps to a section above, and the credential exposure is the first thing to fix.
