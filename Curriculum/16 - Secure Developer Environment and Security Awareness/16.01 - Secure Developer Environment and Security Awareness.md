# Module 16 - Secure Developer Environment and Security Awareness

This outline defines the developer environment and security awareness knowledge assessed in Module 16.

## 16.1 Context and threat model

- Why developer workstations hold source code, credentials, cloud access, and build access in one place
- Why a compromised developer machine can bypass perimeter defenses and reach production
- Assets to protect: source code, credentials, SSH keys, tokens, cloud profiles, test data, browser sessions, and CI/CD configuration
- Common threats: credential theft, malicious packages, compromised extensions, unsafe online tools, insecure remote work, and unsafe local containers
- Insider threats and accidental disclosure as well as external attackers
- Real incidents in which the build or development environment was the entry point

## 16.2 Core principles for secure workstations

- Least privilege for accounts, tools, and cloud access
- Separation of development, test, and production access and credentials
- Defense in depth: no single control protects the workstation
- Secure defaults and the removal of unnecessary software
- Minimizing sensitive data stored locally
- Verifying software, sources, and requests before trusting them
- Baseline controls: full-disk encryption, screen locking, endpoint protection, a host firewall, and timely patching

## 16.3 Policies, roles, and responsibilities

- Why organizational policies exist and what a developer must follow, including acceptable use, software installation, cloud and online-service use, data handling, and production access
- Responsibilities of developers compared with those of managers, security teams, and IT or endpoint management
- Where personal devices, personal accounts, and personal cloud services are allowed or not allowed
- When and how to report a suspected incident, a policy exception, or a security concern
- Why reporting early and without blame supports a faster response

## 16.4 Use of local tools, IDEs, and plugins

- The IDE or editor as an attack surface, since it can read files, run commands, and access the network
- Risks of extensions and plugins: excessive permissions, hijacked or malicious updates, and unknown publishers
- Risks of language servers, build tools, task runners, and command-line utilities that run code from the project
- Workspace trust and why opening an untrusted repository can run code
- Risks of Git hooks and package-manager scripts that run automatically
- Controls: trusted sources, minimal installed tools, restricted permissions, updates, and version pinning or lockfiles (see Module 10, section 10.3)

## 16.5 Use of online services and free tools

- That a free online service can collect, retain, or reuse the content submitted to it
- Online formatters, converters, paste sites, debugging services, and code assistants as places where data leaves organizational control
- Information that must not be submitted: proprietary code, credentials, tokens, customer data, regulated data, and unsanitized logs
- Risk factors: unknown operator, retention, sharing, training on submitted data, and third-party scripts
- Safer alternatives: approved tools, offline or local tools, and sanitized or synthetic sample data
- How to decide whether an online tool is permitted for a given piece of data

## 16.6 Secrets management and sensitive data handling

- What counts as a secret and what counts as sensitive development or test data
- Hard-coded and committed secrets, and why deleting a commit does not remove a secret from history
- Local `.env` files, shell history, and logs as common places where secrets leak
- Approved secret stores, short-lived credentials, and narrowly scoped credentials
- Secret detection in pre-commit checks and repositories
- Rotating and revoking a credential after exposure
- Production data in test environments, and use of synthetic or anonymized data (see Module 8, section 8.4)
- Sensitive data in logs, screenshots, and diagnostic output (see Module 7, section 7.2)
- How developer-side secret handling relates to deployment-side secret handling (see Module 14, section 14.5)

## 16.7 Network, remote access, and home office

- Risks of home, public, and corporate networks
- Approved remote-access methods, VPNs, and equivalent protected access
- Public Wi-Fi risks and the protection that HTTPS and a VPN provide and do not provide
- SSH key protection: passphrases, agents, key types, and separate keys for separate purposes
- Unauthorized tunnels and publicly exposed development services
- Risks of locally running development servers, databases, administrative interfaces, dashboards, and debugging services
- Controls for local services: binding to localhost, authentication, non-default credentials, limited lifetime, and no external exposure
- Physical security in a home or public workspace

## 16.8 Containerized and virtual development environments

- Security benefits of containers, virtual machines, development containers, and cloud workspaces: isolation, repeatability, and disposable environments
- Limitations: containers share the host kernel, and isolation depends on configuration
- Unsafe configurations: privileged containers, mounting the container runtime socket, broad host mounts, running as root, and passing host credentials
- Risks of untrusted base images and images pulled without verification
- Cloud workspaces and managed development environments as shifts in who holds the code and credentials
- How container concerns in development relate to deployment (see Module 14, section 14.8)

## 16.9 Developer awareness and secure habits

- Social engineering aimed at developers: phishing, fake job tests, malicious repositories, pull requests, links, and credential requests
- Supply chain attacks that target developers: typosquatted packages, malicious scripts, and unverified commands (see Module 10, section 10.1)
- Habits: locking unattended devices, using MFA (see Module 2, section 2.3), reviewing commands before running them, and reviewing Git diffs before committing
- Separation of work and personal activities
- Code review as a security control
- Indicators of a possible compromise: unexpected prompts, unknown commits or tokens, unusual account activity, and unexplained processes or network connections
- Immediate responses: stop the activity, preserve evidence, revoke or rotate credentials and sessions, and report to the incident-response process
- Sources of security information: vulnerability advisories, vendor bulletins, organizational guidance, and OWASP resources

## 16.10 Reviewing a developer-environment scenario

- Insecure practices, excessive exposure, and missing controls in a described development setup
- Controls that reduce risk while keeping the development workflow effective
- Ranking issues by likely impact, such as exposed credentials compared with a missing screen lock
- Distinguishing which issues need a policy decision or specialist help and which the developer can fix
