# Supplementary reading - Secure Communications

This chapter covers how web applications protect data in transit and how browsers limit what web content may do.
It explains the basics of Transport Layer Security (TLS) and leaves detailed cipher suite selection to specialist guidance.

## 9.1 Transport security basics

Data sent over a network passes through many systems that the sender does not control, such as Wi-Fi access points, internet providers, and proxies.
Without protection, any of them can read the data (eavesdropping) or change it (tampering).
An attacker who sits between two parties and can read or change their traffic is performing a man-in-the-middle (MITM) attack.

Transport Layer Security (TLS) is the protocol behind HTTPS.
It gives a connection three properties:

- Confidentiality, because the content is encrypted so that eavesdroppers cannot read it
- Integrity, because modification of the traffic is detected
- Endpoint authentication, because the client checks that it is talking to the intended server

TLS protects data only while it travels between the two endpoints of a connection.
It does not decide who is allowed to use the application.
A user connected over TLS still needs authentication and authorization.
TLS also does not protect data after it arrives.
The server can still write a password to a log file, and a browser can still keep a page in its cache.
Modules 7 and 8 cover those risks.

### Versions and configuration

TLS has been revised several times.
The names SSL 2.0 and SSL 3.0 belong to its predecessors, and TLS 1.0 and 1.1 are also obsolete ([RFC 8996](https://www.rfc-editor.org/info/rfc8996) formally deprecates them).
TLS 1.2 and TLS 1.3 ([RFC 8446](https://www.rfc-editor.org/info/rfc8446)) are the versions in current use.
Prefer TLS 1.3 where both sides support it.

A cipher suite is the set of algorithms that a connection uses.
A developer rarely needs to pick them one by one.
Current versions of web servers, frameworks, and TLS libraries ship with sensible defaults, and TLS 1.3 removed the weak options altogether.
When a configuration is needed, start from a maintained recommendation, such as the [Mozilla Server Side TLS guidelines](https://wiki.mozilla.org/Security/Server_Side_TLS) and the [Mozilla SSL Configuration Generator](https://ssl-config.mozilla.org/), and avoid editing cipher lists by hand.
The practical warning signs are options that name NULL ciphers (no encryption), export-grade ciphers, RC4, or old protocol versions, because these are known to be broken or weak.

For the same reason, use the TLS support of a maintained library, framework, or managed service instead of writing transport security yourself.
Custom protocols tend to contain mistakes that the established ones fixed years ago.
Using a library does not remove the need for configuration, such as enabling certificate verification and disabling old versions.

### Forward secrecy

An attacker may record encrypted traffic today and hope to steal the server's private key later.
Forward secrecy prevents this from exposing old sessions.
With it, each connection uses temporary (ephemeral) keys that are discarded afterward, so the long-term private key alone cannot decrypt recorded traffic.
TLS 1.3 uses ephemeral key exchange for every connection.
In TLS 1.2, it depends on the chosen cipher suite.
Note that forward secrecy is separate from authentication: the certificate still proves who the server is, while ephemeral keys limit the damage of a later key leak.

## 9.2 Certificates and trust

A certificate links a public key to an identity, such as a domain name.
A certificate authority (CA) signs the certificate to vouch for that link.
Operating systems and browsers ship a list of CAs they trust.
A server usually sends its certificate together with intermediate certificates that connect it to one of those trusted CAs.

### What a client checks

When a client connects, it verifies that:

- The certificate chain leads to a CA the client trusts
- The certificate matches the host name the client intended to reach
- The current time falls inside the certificate's validity period

All three checks matter.
A valid certificate for a different host name proves nothing about the host the client wanted to reach.
Revocation (see below) can add a further check, though its support varies.

### Validation failures and safe responses

Typical causes of a validation failure are:

- An expired certificate, often because renewal was forgotten
- A missing intermediate certificate on the server
- A host name that is not listed in the certificate
- A certificate from an issuer that the client does not trust, such as an internal CA or a self-signed certificate
- A client with a wrong clock

A common and dangerous shortcut is to turn verification off.
Examples include `verify=False` in an HTTP client, a trust manager that accepts every certificate, or an option that skips the host name check.
These shortcuts remove endpoint authentication, so a man-in-the-middle attacker can present any certificate.
They often start as a temporary fix for a test environment and then reach production.

Safer responses address the cause:

- Renew an expired certificate and automate renewal to avoid repeating the failure
- Configure the server to send the full chain, including intermediate certificates
- Issue a certificate that includes the correct host name
- Add the organization's private CA to the trust store of the clients that need it, instead of disabling verification
- Fix the system clock

If the connection still fails, treat that as the correct result.
An application should refuse to send data to an endpoint it cannot verify.

### Certificate lifecycle and private keys

A certificate goes through issuance, use, renewal, and replacement.
Certificates expire on purpose, so that mistakes and stolen keys have a limited lifetime.
Automated issuance, for example through the ACME protocol ([RFC 8555](https://www.rfc-editor.org/info/rfc8555), used by [Let's Encrypt](https://letsencrypt.org/how-it-works/)), removes much of the manual work that leads to expired certificates.

The private key is the secret that proves the server's identity.
Keep it out of source control and container images, limit who can read it, and use a secrets store or a hardware-backed key store where available (Module 5 covers key management).
If a private key may have been exposed, replacing the certificate is not enough on its own.
Generate a new key pair, obtain a new certificate, and revoke the old one with the CA ([Let's Encrypt describes the process](https://letsencrypt.org/docs/revoking/)).
Revocation checking in clients is not fully reliable, so a short certificate lifetime also helps.

Certificate scope matters too.
A wildcard certificate covers every subdomain of a domain.
If its key leaks, the attacker can impersonate any of those hosts, so avoid sharing one wildcard key across many systems.

Two additional controls help detect or restrict issuance:

- Certificate Transparency (CT) is a set of public logs of issued certificates.
  Domain owners can monitor them to notice certificates they did not request.
  See [How CT works](https://certificate.transparency.dev/howctworks/).
- A DNS CAA record lists the CAs that may issue certificates for a domain ([RFC 8659](https://www.rfc-editor.org/info/rfc8659), and the [Let's Encrypt CAA documentation](https://letsencrypt.org/docs/caa/)).
  CAs are required to check it before issuing, but clients do not check it when they connect.

### Certificate pinning

Pinning goes further than trusting every CA on the system list.
A client that pins keeps a copy of the expected certificate, or of its public key, and rejects any other.
A stolen or wrongly issued certificate from another CA then fails the check.
Pinning applies mainly to clients under the developer's control, such as mobile apps and API clients.
Web browsers dropped their pinning feature, HTTP Public Key Pinning ([RFC 7469](https://www.rfc-editor.org/info/rfc7469)), because mistakes could lock sites out, and it is not part of this curriculum.
Android, for example, supports pins through its [network security configuration](https://developer.android.com/privacy-and-security/security-config).

Pinning also carries operational risk.
If the server changes its certificate or key and the pin is not updated, every pinned client fails to connect.
Pin to the public key rather than the whole certificate when possible, so a renewed certificate with the same key still matches.
Include a backup pin for a key that is prepared but not yet in use, and plan how apps receive updated pins.
When a pin does not match, the client should fail the connection.
An emergency "ignore pin errors" switch undoes the protection.
If pinning is too costly to maintain, CAA records, Certificate Transparency monitoring, and short-lived certificates are alternatives that reduce the same risk with less client-side effort.
The [OWASP Pinning Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Pinning_Cheat_Sheet.html) discusses these trade-offs.

## 9.3 Enforcing HTTPS in browsers

### HTTPS redirection

Users often type a plain domain name, so the browser's first request may use HTTP.
A server redirects that request to the HTTPS address ([redirections overview](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Redirections)).
The redirect is itself sent over HTTP.
An attacker on the network can therefore tamper with that first request or response and keep the user on HTTP.
Redirection is necessary, but it does not stop this on its own.

### HTTP Strict Transport Security (HSTS)

HSTS closes that gap.
A site sends the response header over HTTPS:

```
Strict-Transport-Security: max-age=31536000; includeSubDomains
```

The browser remembers the instruction for `max-age` seconds (31536000 is one year).
During that time it changes any HTTP request for that host to HTTPS before sending it, and it refuses to continue past certificate errors for that host.
The header is ignored when it arrives over plain HTTP ([RFC 6797](https://www.rfc-editor.org/info/rfc6797), [MDN reference](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Strict-Transport-Security)).

`includeSubDomains` extends the rule to every subdomain.
This is useful, but a subdomain that only supports HTTP becomes unreachable for returning visitors.
Confirm that all subdomains work over HTTPS first.
Start with a short `max-age` and raise it after the site has been checked.

HSTS has a first-connection limitation.
The browser has not yet seen the header on its first visit, or after the stored entry expires.
Preloading addresses this.
Browsers ship a built-in list of HSTS domains, and a site can request inclusion through [hstspreload.org](https://hstspreload.org/) by sending the `preload` token with a long `max-age` and `includeSubDomains`.
Removal from the list takes a long time because it depends on browser releases, so preload only when all subdomains are committed to HTTPS.

### Mixed content

Mixed content occurs when a page loaded over HTTPS includes resources over HTTP.
Passive content, such as images, can be changed to mislead the user.
Active content, such as scripts and stylesheets, is more dangerous because an attacker who changes it can control the whole page.
Browsers block active mixed content and upgrade or block passive content ([MDN: Mixed content](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Mixed_content)).
The fix is to load every resource over HTTPS.

Two Content Security Policy (CSP) directives help here:

- [`upgrade-insecure-requests`](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/upgrade-insecure-requests) tells the browser to treat `http://` URLs for the page's resources as `https://`.
  It helps with large sites that still contain old links, but the resources must actually be available over HTTPS.
- [`connect-src`](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/connect-src) limits the URLs that scripts can contact through `fetch`, XMLHttpRequest, WebSocket, and similar APIs.
  It can be used to allow only specific HTTPS and `wss://` destinations.

Neither directive replaces TLS on the server, HSTS, or authorization on the server side.
They only constrain what the browser does.

### The Secure cookie attribute

A cookie with the `Secure` attribute is sent only over HTTPS.
Without it, the browser also sends the cookie on plain HTTP requests, where an eavesdropper can read it.
This is how a session cookie can be stolen even when the site redirects to HTTPS.
`Secure` does not encrypt the value in storage, does not prevent scripts from reading the cookie (`HttpOnly` does), and does not prevent cross-site requests (`SameSite` and CSRF protections do).
Module 2 (sections 2.4 and 2.5) owns the cookie attributes and cross-site request forgery (CSRF).
Refer to it for the complete treatment.
The [MDN cookie guide](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Cookies) also covers the attributes.

## 9.4 Connections between components

A modern application is a chain of connections: browser to load balancer, load balancer to application, application to database, and application to external APIs.
Each link needs its own protection.
Secure browser traffic does not make the later links secure.

### TLS termination

Many deployments end TLS at a reverse proxy or load balancer.
This is called TLS termination.
It offloads certificate handling and lets the proxy inspect requests.
After the termination point, traffic often continues in plaintext to the application.
This is acceptable only when that network segment is controlled and trusted.
In shared, cloud, or multi-tenant networks, anyone with network access can read it.
Options are to re-encrypt the traffic from the proxy to the application, or to pass the encrypted connection through and terminate it at the application.
In both cases the proxy should verify the certificate of the backend.

An application behind a proxy sees HTTP requests.
It learns the original protocol and client address only from headers such as `X-Forwarded-Proto`.
Accept those headers only from the known proxy, because a client can send forged ones.
Otherwise, a redirect to HTTPS may loop, or security decisions may rely on spoofed values.

### Outbound connections and fallback to plaintext

Calls from an application to a payment provider, a mail service, or an internal API are also TLS connections, and the application is the client.
It must verify the server certificate as a browser would (see section 9.2).
Many bugs here come from copied code that turns verification off.

Also watch for fallback to plaintext.
Examples are a database or mail driver with "use TLS if available", a client that retries over HTTP when HTTPS fails, or a URL configured as `http://` in one environment.
An attacker who can block or alter the first attempt can force the downgrade.
Require TLS, and treat failure as an error.

### Mutual TLS

In ordinary (server-authenticated) TLS, only the server presents a certificate.
The client is identified separately, for example by a password or token.
In mutual TLS (mTLS), the client also presents a certificate, and the server validates it against a CA that it trusts.
Both sides are thus authenticated at the connection level.

mTLS is common for service-to-service communication, for API clients that are partner systems, and for devices.
The server can read the verified identity from the client certificate, such as its subject or subject alternative name, and use it as an input to access decisions.
A verified certificate, however, answers only "who is this?" and not "what may it do?".
The application must still check authorization for each request.
For example, any internal service with a valid certificate from the company CA should not automatically be allowed to call an administrative endpoint.
mTLS also needs certificate issuance, renewal, and revocation processes for every client.
The [OWASP Microservices Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Microservices_Security_Cheat_Sheet.html) discusses service-to-service identity.

## 9.5 WebSockets

A WebSocket ([RFC 6455](https://www.rfc-editor.org/info/rfc6455)) is a long-lived, two-way connection between a browser and a server.
It starts as an HTTP request that is upgraded.
Applications use it for chat, live dashboards, and notifications.

The URL scheme `ws://` is unencrypted.
The scheme `wss://` runs over TLS and gives the protections described in section 9.1.
Use `wss://` for everything except local development.
The risks below remain even with `wss://`:

- Cross-Site WebSocket Hijacking.
  Browsers do not apply the same-origin policy to WebSocket connections, and they attach the user's cookies to the handshake.
  A malicious page can therefore open a connection to your server using the visitor's session.
  Check the `Origin` header during the handshake against an allowed list, and do not rely on cookies alone for authentication.
- Authentication and authorization.
  Authenticate the connection when it starts, and check the user's permission for each action or channel, because a connection may last for hours.
- Message validation.
  Treat every message as untrusted input in the same way as an HTTP parameter (Module 4).
- Resource limits.
  A single connection stays open and consumes memory.
  Set limits on message size, message rate, connections per user, and idle time to resist abuse.
- Connection termination.
  Close the connection when the session ends, the user logs out, or access is revoked.

Do not put tokens in the `ws://` or `wss://` URL when avoidable, because URLs end up in logs.
The [OWASP WebSocket Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/WebSocket_Security_Cheat_Sheet.html) lists further measures.
For a hands-on explanation of the hijacking attack, see the [PortSwigger Web Security Academy page on WebSockets](https://portswigger.net/web-security/websockets).

## 9.6 Browser security model

Most of the controls in this section run in the browser and are enforced by it.
They limit the damage when something else goes wrong.
They do not replace correct server-side code.

### Same-origin policy

An origin is the combination of scheme, host, and port.
`https://example.com` and `https://example.com:8443` are different origins, and so are `https://example.com` and `http://example.com`.
The same-origin policy (SOP) is a browser rule that prevents a script from one origin from reading responses from another.
Without it, any website you visit could read your webmail in the background using your logged-in session.
See [MDN: Same-origin policy](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Same-origin_policy) and [RFC 6454](https://www.rfc-editor.org/info/rfc6454).

The SOP restricts reading.
It does not stop the browser from sending a request to another origin, such as a form post, and the request carries cookies.
This is why cross-site request forgery exists (see Module 2, section 2.5).

### Cross-origin resource sharing (CORS)

Sometimes a site must allow another origin to read its responses, for example a single-page application on `app.example.com` that calls an API on `api.example.com`.
Cross-origin resource sharing (CORS) lets the server relax the SOP with response headers such as `Access-Control-Allow-Origin`.
For some requests the browser first sends a "preflight" `OPTIONS` request to ask whether the real request is allowed ([MDN: CORS](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS)).

CORS is not an access-control feature for the server.
It tells the browser whether to let a page's script read a response.
The server still receives and processes the request, and non-browser clients ignore CORS entirely.
CORS also does not protect against CSRF, because the request is sent anyway.

Common misconfigurations are:

- Copying the request's `Origin` header into `Access-Control-Allow-Origin` without checking it against an allowed list
- Allowing the origin value `null`
- Sending `Access-Control-Allow-Credentials: true` for origins that are not fully trusted, which lets those sites read authenticated responses
- Allowing broad patterns, such as any subdomain, when one subdomain is less secure than the rest

Browsers do not allow the wildcard `*` together with credentials, which is why servers sometimes reflect the origin instead.
Keep an explicit allowlist of origins and do not enable credentials unless required.
The [PortSwigger CORS guide](https://portswigger.net/web-security/cors) shows how these mistakes are exploited.

### Content Security Policy

Content Security Policy (CSP) is a response header that tells the browser which sources it may load scripts, styles, images, frames, and connections from.
A strict policy that blocks inline scripts and unknown script sources can stop injected script from running even if an XSS flaw exists.
It is a second line of defense.
Output encoding remains the primary defense (Module 4, section 4.4).
See the [MDN CSP guide](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CSP).
Google's [CSP Evaluator](https://csp-evaluator.withgoogle.com/) is a tool that highlights weak policies, such as those that allow `unsafe-inline`.

### Clickjacking and framing

In clickjacking, an attacker loads your site in a transparent frame on their own page and tricks the user into clicking something, such as a "confirm transfer" button.
The defense is to tell the browser which origins may frame your pages.
The CSP directive [`frame-ancestors`](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/frame-ancestors) does this: `frame-ancestors 'none'` blocks all framing, and `frame-ancestors 'self'` allows only the same origin.
The older `X-Frame-Options` header (`DENY` or `SAMEORIGIN`) has the same purpose and is still sent for older browsers.
Modern browsers prefer `frame-ancestors` when both are present.
See the [PortSwigger clickjacking guide](https://portswigger.net/web-security/clickjacking) for examples.

### Other security headers

Two more headers are short and widely recommended:

- `X-Content-Type-Options: nosniff` stops the browser from guessing a content type different from the one the server declared.
  This prevents, for example, a user-uploaded text file from being run as a script ([MDN](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/X-Content-Type-Options)).
- `Referrer-Policy` controls how much of the current URL is sent to other sites in the `Referer` header.
  URLs may contain tokens or identifiers, so a restrictive policy limits leakage ([MDN](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Referrer-Policy)).

Together with HSTS (section 9.3), CSP, and `frame-ancestors`, these form a basic header set.
The [OWASP HTTP Headers Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/HTTP_Headers_Cheat_Sheet.html) and [Secure Headers Project](https://owasp.org/projects/secure-headers-project) list current recommendations.
Remember that headers supplement secure code and do not replace it.

## Worked example

A team deploys an application behind a cloud load balancer.
The load balancer terminates TLS and forwards plain HTTP to the application servers.
The application calls a partner API and shows an embedded dashboard over a WebSocket.

A review finds several issues:

1. HTTP requests are redirected to HTTPS, but no HSTS header is sent.
  A user on public Wi-Fi who types the plain domain can still be intercepted on the first request.
  The team adds `Strict-Transport-Security` with a short `max-age` and increases it after checking subdomains.
2. The page loads an old script over `http://`.
  Browsers block it, so a feature is broken.
  Rather than relying on `upgrade-insecure-requests`, the team changes the URL to HTTPS.
3. The partner API client was set to ignore certificate errors during a test.
  The partner's certificate has a missing intermediate on their server.
  The team removes the bypass and asks the partner to fix the chain, instead of disabling verification.
4. The traffic between load balancer and application crosses a shared network.
  The team enables TLS between them and has the load balancer verify the application's certificate.
5. The WebSocket handshake relies on the session cookie only.
  A malicious page could open a connection for a logged-in visitor.
  The team checks the `Origin` header, requires authorization for every channel subscription, and limits message size.
6. The API for the single-page front end reflects any `Origin` and allows credentials.
  The team replaces this with an explicit allowlist.
7. The dashboard can be framed by any site.
  The team adds `frame-ancestors 'self'`.

Each fix targets a different property: verification of the endpoint, protection of each link, and limits on what other origins can do.
