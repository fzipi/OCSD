# Module 13 - API and Web Service Security

This outline defines the API and web service security knowledge assessed in Module 13.

## 13.1 API risks and the OWASP API Security Top 10

- The difference between an API and a browser-rendered web application, including machine clients and structured data
- Why APIs expose more of an application's objects, properties, and functions to direct calls
- The ten risks of the OWASP API Security Top 10:2023, by name and number
- Broken object level authorization, broken object property level authorization, and broken function level authorization as distinct failures
- Broken authentication, unrestricted resource consumption, and unrestricted access to sensitive business flows
- Server-side request forgery, security misconfiguration, improper inventory management, and unsafe consumption of APIs
- The relationship between the API Security Top 10 and the OWASP Top 10 for web applications
- Undocumented, outdated, and unmaintained API versions and endpoints as an attack surface

## 13.2 API authentication and authorization

- Authentication as identifying the caller and authorization as deciding what that caller may do
- API keys as identifiers of an application or project and their limits as proof of a user's identity
- Access tokens as credentials issued by an authorization server and presented to an API
- OAuth 2.0 as a delegated authorization framework, and the distinction between OAuth 2.0 and authentication
- The authorization code flow with PKCE for user-delegated access and the client credentials flow for service-to-service access
- Scopes as a limit on what a token allows, and the need for object-level checks beyond scopes
- Token verification by the API, including signature, issuer, audience, and expiry; JWT validation is covered in Module 2 (section 2.5)
- Exposure of keys and tokens in URLs, logs, source code, and client-side code
- Object-level, property-level, and function-level authorization enforced in the API for every request, as defined in Module 3 (section 3.4)
- Client-supplied identifiers, roles, and tenants treated as untrusted
- An API gateway as a central enforcement point that does not replace authorization in the service

## 13.3 Resource consumption and automated abuse

- Request rate, request size, response size, pagination, and processing time as consumable resources
- Per-client, per-endpoint, and global rate limits
- Quotas, HTTP 429 responses, and retry information for clients
- Costs of third-party calls, such as messages sent or paid services, as a target of abuse
- Credential stuffing and brute force against authentication endpoints as API abuse
- Sensitive business flows, such as sign-up, purchase, and password reset, as targets of automation; anti-automation controls are covered in Module 11 (section 11.5)

## 13.4 Request validation and response handling

- Requests as untrusted input in every part: path, query, headers, and body
- Schema-based validation of types, formats, lengths, ranges, and required properties, for example with OpenAPI or JSON Schema
- Rejection of unexpected properties and unexpected content types
- Mass assignment when request properties are bound directly to internal objects
- Excessive data exposure when responses return whole internal objects
- Maximum request body sizes and parser limits
- Injection through API inputs; injection prevention is covered in Module 4 (section 4.3)
- Generic error responses that do not reveal internal details; error handling is covered in Module 6
- Correct content-type headers on responses

## 13.5 REST API security

- HTTP methods as part of the access-control decision
- Safe methods that must not change state
- Transport encryption for all API traffic, as covered in Module 9
- Stateless authentication with a token on each request
- Sensitive data in URLs, which may be logged, cached, or shared
- Meaningful HTTP status codes without detail that helps an attacker
- API versioning, deprecation, and retirement as part of inventory management
- Cache-control headers for responses that contain sensitive data
- Cross-origin access from browsers; CORS and other browser-enforced controls are covered in the browser security topic of Module 9

## 13.6 GraphQL security

- GraphQL as a single endpoint where the client chooses the shape and amount of data
- Query depth, complexity, and cost as sources of denial of service
- Batching and aliases as ways to bypass per-request rate limits
- Authorization at the field and resolver level rather than only at the endpoint
- Introspection and verbose errors as sources of information disclosure in production
- Injection through variables and resolver arguments

## 13.7 SOAP and gRPC security

- SOAP as an XML-based messaging protocol and gRPC as a binary protocol using Protocol Buffers
- XML external entity injection as a risk of SOAP and other XML parsing; see Module 4 (section 4.3)
- WS-Security as message-level protection for SOAP, compared with transport-level protection
- TLS and mutual TLS for gRPC channels, as covered in Module 9 (section 9.7)
- Authentication and authorization for each gRPC call
- The need to validate request messages even when a schema defines their structure

## 13.8 Webhooks and third-party APIs

- A webhook as an HTTP request that a service sends to a URL registered by a consumer
- Missing sender verification, replay of captured requests, and unencrypted delivery as webhook risks
- Signature verification using a shared secret, and timestamps as a defense against replay
- Server-side request forgery when users register webhook URLs; see Module 12 (section 12.10)
- Data from third-party APIs as untrusted input
- Validation of third-party responses, timeouts, and failure handling
- Least-privilege scopes and secure storage for credentials issued by third parties

## 13.9 API security testing

- Testing authentication, authorization, and rate limits with multiple users and roles
- Testing object-level and function-level authorization by changing identifiers and calling other users' endpoints
- Testing input handling with malformed, oversized, and unexpected requests
- Fuzzing as automated testing with unexpected input
- Use of an API description such as OpenAPI to generate test cases
- Automated API security tests in a continuous integration pipeline
- Business logic testing of API workflows; see Module 11 (section 11.12)
