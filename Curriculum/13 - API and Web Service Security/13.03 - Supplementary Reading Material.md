# Supplementary reading - API and Web Service Security

This chapter explains the security risks of APIs and web services and the controls that reduce them.
It builds on the authentication, authorization, input validation, and secure communication modules, and points to them instead of repeating them.

## API risks and the OWASP API Security Top 10

An application programming interface (API) lets one program call another.
A web service is an API offered over HTTP.
A mobile app, a single-page web application, a partner system, and another internal service can all call the same API.

A browser-rendered application controls what a user sees.
An API returns structured data, usually JSON or XML, and the caller decides how to use it.
Attackers therefore do not need the user interface.
They read the API description or observe traffic, and then call endpoints directly with changed identifiers, extra properties, or unusual volumes.
Three properties make APIs a distinct target:

- APIs expose objects, properties, and functions directly, so every one needs its own access check.
- Clients are often programs, so an attacker can automate thousands of requests.
- APIs are often numerous and change often, so old or undocumented versions are easy to forget.

OWASP maintains a separate [API Security Top 10](https://api-security.owasp.org/editions/2023/en/0x11-t10/) for this reason.
The current edition is 2023, and no newer edition had been published when this chapter was written.
The ten risks are:

| Risk | What goes wrong |
|---|---|
| API1:2023 Broken Object Level Authorization | A caller reads or changes another user's object by changing an identifier. |
| API2:2023 Broken Authentication | Authentication can be bypassed, guessed, or replayed. |
| API3:2023 Broken Object Property Level Authorization | A caller reads or writes properties of an object that the caller should not access. |
| API4:2023 Unrestricted Resource Consumption | Requests use up CPU, memory, bandwidth, or paid services. |
| API5:2023 Broken Function Level Authorization | A caller uses a function reserved for another role, such as an administrative endpoint. |
| API6:2023 Unrestricted Access to Sensitive Business Flows | A flow such as ticket purchase or account creation is automated to harm the business. |
| API7:2023 Server Side Request Forgery | The API fetches an attacker-chosen URL from inside the network. |
| API8:2023 Security Misconfiguration | Insecure defaults, missing hardening, or verbose errors expose the API. |
| API9:2023 Improper Inventory Management | Old, test, or undocumented API versions and hosts remain reachable. |
| API10:2023 Unsafe Consumption of APIs | The API trusts data from another API without checking it. |

Three of these risks are about the same question asked at different levels: may this caller do this to this thing?
Object level asks about a specific record, property level asks about a field in that record, and function level asks about the operation itself.
Module 3 (section 3.4) defines these failures, and Module 12 (section 12.8) covers server-side request forgery.

The API Security Top 10 does not replace the OWASP Top 10 for web applications.
For example, [A01:2025 Broken Access Control](https://top10.owasp.org/2025/A01_2025-Broken_Access_Control/) covers the web application view of API1, API3, and API5.
Use both lists when reviewing an API.

Improper inventory management deserves attention because it is easy to overlook.
A forgotten `v1` endpoint may lack protections added to `v2`.
A test host with production data may have no authentication.
A maintained inventory lists each API host, version, owner, data it handles, and retirement date.

## API authentication and authorization

Authentication identifies the caller.
Authorization decides what that caller may do.
An API must perform both on every request, because it cannot rely on a user interface to hide functions.

### API keys

An API key is a secret string that identifies the application or project calling the API.
Keys are simple to issue but have limits:

- A key usually identifies a program, not a person.
- A key does not expire unless the provider sets an expiry.
- Anyone who holds the key can use it.

Keys should be generated randomly, stored as secrets, limited to the permissions the client needs, and rotated.
Keys must not appear in URLs, because URLs are recorded in logs, browser history, and proxies.
Keys must not appear in source code or in client-side code that users can read.
The [OWASP Secrets Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html) covers storing and rotating them.

### OAuth 2.0 access tokens

OAuth 2.0, defined in [RFC 6749](https://www.rfc-editor.org/info/rfc6749), is a framework that lets a client obtain limited access to an API.
An authorization server issues an access token, and the client sends the token to the API.
OAuth 2.0 delegates authorization.
It does not by itself tell the API who the user is; OpenID Connect adds authentication on top of OAuth 2.0 (see Module 2, section 2.6).

Two flows matter most for APIs:

- The authorization code flow with Proof Key for Code Exchange (PKCE, [RFC 7636](https://www.rfc-editor.org/info/rfc7636)) is for a user who grants an application access to their data.
  PKCE protects the code from being used by anyone other than the client that requested it.
- The client credentials flow is for service-to-service calls where no user is present.
  The client authenticates to the authorization server with its own credentials.

The [OAuth 2.0 Security Best Current Practice (RFC 9700)](https://www.rfc-editor.org/info/rfc9700) recommends PKCE for all clients using the authorization code flow and discourages older flows such as the implicit grant.
The [OWASP OAuth 2.0 Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/OAuth2_Cheat_Sheet.html) gives the OWASP view.

### Verifying tokens

An API that receives an access token must verify it before trusting it.
Decoding a token only reads its content.
Verification checks that the token was issued by the expected authorization server, was meant for this API, has not expired, and has a valid signature or a successful introspection result.
Module 2 (section 2.6) owns the details of JWT validation, such as fixing the accepted algorithm and checking the issuer, audience, and expiry claims.
[RFC 8725](https://www.rfc-editor.org/info/rfc8725) lists the common mistakes.

### Scopes are not object-level authorization

A scope is a label in a token that limits what the token allows, such as `invoices:read`.
A scope answers whether the client may read invoices at all.
It does not answer whether this user may read invoice 987654.
The API must still check the specific object against the identity in the token.

A vulnerable handler looks up the object by the identifier in the request and returns it.
A correct handler also checks that the authenticated caller may access that object, and returns the same error for a missing object and a forbidden one when the difference would reveal that the object exists.

### Authorization for every request

Authorization checks belong in the API code or in a reusable component that every endpoint passes through.
The same rules apply to every route and HTTP method, including routes that no user interface calls.
Values that the client controls, such as user identifiers, roles, and tenant names in the body or headers, are untrusted.
The server derives identity from the verified token and loads permissions from its own data.
Module 3 (sections 3.3 and 3.4) covers the model and the common failures.

An API gateway is a server in front of one or more APIs that can authenticate callers, check scopes, and limit rates.
A gateway is a good place for checks that are the same for every endpoint.
It rarely knows which records belong to which user.
Object-level and property-level checks therefore remain in the service.

## Resource consumption and automated abuse

Every request consumes resources: CPU time, memory, database queries, bandwidth, and sometimes paid services such as text messages or payment checks.
Unrestricted resource consumption (API4:2023) occurs when a caller can use more than is intended, either by sending many requests or by sending a few expensive ones.

Limits can apply to several things:

- The number of requests in a time window
- The size of the request body and of uploaded files
- The number of items a list endpoint may return, through a maximum page size
- The time a request may run before it is stopped
- The number of calls to paid or slow downstream services

A rate limit restricts how many requests a client may send in a period.
A quota is a longer-term allowance, such as requests per month.
Limits can be set per client, per endpoint, or globally.
Expensive endpoints, such as search, export, and password reset, need stricter limits than simple reads.
A per-client limit is only as good as the client identity, so a limit keyed only on an IP address is easy to bypass and can penalize many users behind one address.

When a client exceeds a limit, the API responds with HTTP status 429 (Too Many Requests, defined in [RFC 6585](https://www.rfc-editor.org/info/rfc6585)).
The response can include a `Retry-After` header.
A standard for rate-limit headers is still a draft: [RateLimit header fields for HTTP](https://datatracker.ietf.org/doc/draft-ietf-httpapi-ratelimit-headers/).

Authentication endpoints are a special target.
In credential stuffing, an attacker tries username and password pairs leaked from other sites.
In brute force, an attacker tries many guesses for one account.
Limits per account and per client, together with the credential protections in Module 2, reduce both.

Some abuse uses valid requests at a harmful scale, such as buying all tickets or creating thousands of accounts.
OWASP lists this as API6:2023 Unrestricted Access to Sensitive Business Flows.
The defense starts with identifying which business flows are valuable to abuse, then adding controls that suit them.
Module 11 (section 11.5) owns anti-automation controls.
The [OWASP Denial of Service Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Denial_of_Service_Cheat_Sheet.html) lists related resource limits.

## Request validation and response handling

Every part of an API request is untrusted input: the path, query string, headers, and body.
Module 4 explains validation and injection prevention.
This section covers what is specific to APIs.

### Validating against a schema

Many APIs have a machine-readable description, such as an [OpenAPI](https://spec.openapis.org/oas/latest.html) document, which can include a JSON Schema for each request body.
Validating each request against the schema rejects wrong types, missing required properties, values outside allowed ranges, and unexpected properties.
Rejecting unexpected properties matters because of mass assignment.

### Mass assignment and excessive data exposure

Mass assignment happens when the API copies all properties of a request into an internal object.
If the internal object has a property such as `isAdmin` or `accountBalance`, a caller can include it in the request and set it.
The fix is to accept only the properties each operation allows and to map them explicitly.

Excessive data exposure is the response-side counterpart.
It happens when the API returns the whole internal object and relies on the client to display only some fields.
The attacker reads the raw response.
Both problems are examples of API3:2023 Broken Object Property Level Authorization.
The fix is the same in both directions: define per operation and per role which properties may be read or written.

### Size, content type, and parsers

The API should reject request bodies above a maximum size before parsing them.
It should also accept only the content types it expects and respond with the correct `Content-Type` header.
A parser that accepts deeply nested JSON or large XML can be made to use a lot of memory, so parser limits matter.

### Injection

Values from the request that reach a database, shell, or other interpreter must be handled with parameterized APIs, as Module 4 (section 4.3) explains.
APIs add one trap: JSON bodies can contain objects and arrays where the code expects a string.
In some NoSQL databases, a request value such as `{"$ne": ""}` can then change the meaning of a query.
Checking that each value has the expected type prevents this.

### Errors

Error responses should tell a client enough to fix a request without revealing stack traces, query text, file paths, or software versions.
A consistent error format with a generic message and a correlation identifier helps legitimate users and support staff.
Module 6 covers error handling.
The [OWASP Error Handling Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Error_Handling_Cheat_Sheet.html) gives guidance.

## REST API security

Representational State Transfer (REST) is a style that exposes resources through URLs and uses HTTP methods to act on them.
Most web APIs follow it loosely.
The [OWASP REST Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/REST_Security_Cheat_Sheet.html) lists the main practices.

### Methods and status codes

HTTP methods carry meaning, defined in [RFC 9110](https://www.rfc-editor.org/info/rfc9110).
`GET` is a safe method: it should not change state.
If a `GET` request can delete or change data, link prefetchers, crawlers, and cross-site requests can trigger the change.
Access control should consider the method as well as the path, because a user who may `GET` a resource may not be allowed to `PUT` or `DELETE` it.
The API should reject methods it does not support instead of treating them as a default.

Status codes should match the outcome: `401` for missing or invalid credentials, `403` for an authenticated caller who lacks permission, `404` for a missing resource, and `429` for rate limiting.
Responses should not give more detail than a legitimate client needs.

### Transport and tokens

All API traffic should use TLS, as Module 9 describes.
REST APIs are usually stateless: the client sends a token with every request, typically in the `Authorization` header.
Tokens in the URL are logged and can leak through referrer headers.
Responses that contain sensitive data should carry cache-control headers that prevent shared caches from storing them.
The [OWASP HTTP Headers Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/HTTP_Headers_Cheat_Sheet.html) lists useful response headers.

### Versioning and retirement

APIs change, and clients upgrade slowly, so several versions often run at once.
Each version is attack surface.
Security fixes must reach every supported version, and retired versions must actually be shut down.
This is the practical side of API9:2023.

### Calls from browsers

When a web page in a browser calls an API on a different origin, the browser enforces the same-origin policy and uses Cross-Origin Resource Sharing (CORS) to relax it.
CORS, security headers, and cookie attributes are controls enforced by browsers.
Module 9 teaches them in its browser security topic; this module does not repeat them.
One point matters for API designers: CORS does not protect an API from non-browser clients, so it never replaces authentication and authorization.

## GraphQL security

GraphQL is a query language for APIs.
A GraphQL API usually has one endpoint, and the client sends a query that names the objects and fields it wants.
The server's schema defines the available types and fields.
The [GraphQL documentation](https://graphql.org/learn/) and [specification](https://spec.graphql.org/) describe the language.

This design creates security concerns that REST endpoints do not have.

### Expensive queries

Types in a GraphQL schema often refer to each other, for example a user has posts and each post has comments written by users.
A client can write a deeply nested query, or ask for a very large list at each level, and force the server to do a great deal of work with one request.
Common controls are limits on query depth, a cost or complexity estimate for each query with a maximum, limits on page sizes, and a timeout.

### Batching and aliases

GraphQL lets a client send several operations in one HTTP request, and lets one query call the same field several times using aliases.
An attacker can try hundreds of password guesses or one-time codes in a single request.
A rate limit that counts HTTP requests does not detect this.
Limits should count operations or cost, and sensitive operations such as login should restrict aliases and batching.

### Authorization in resolvers

A resolver is the function that returns the data for a field.
Because clients can reach one object through many paths, for example directly or through a related object, checking access only at the top-level query leaves other paths open.
Authorization is safest in the shared business layer that every resolver calls, as Module 3 (section 3.3) recommends.
Field-level authorization matters because a type may have fields that only some roles may read.

### Introspection and errors

Introspection is a GraphQL feature that lets a client ask the server to describe its full schema.
It helps development tools.
In production it also gives attackers a map of every type and field, including ones not meant for public use.
Introspection should be disabled or restricted for production APIs that are not public.
Disabling it does not remove the need for authorization, because attackers can still guess field names, and some servers suggest similar names in error messages.
Verbose errors and debug output should be turned off.

### Injection

Variables and resolver arguments reach databases and other systems.
They need the same validation and parameterized queries as other input.
The [OWASP GraphQL Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/GraphQL_Cheat_Sheet.html) lists these controls.

## SOAP and gRPC security

REST and GraphQL usually exchange JSON.
Two other styles remain in use, especially between organizations and between internal services.
This section covers only what a developer must recognize.

### SOAP

SOAP is a protocol that wraps requests and responses in XML messages, defined by the [W3C SOAP specification](https://www.w3.org/TR/soap12-part1/).
A service description, the WSDL file, lists the operations and message formats.
Two concerns are specific to SOAP:

- Parsing XML can be unsafe.
  XML external entity (XXE) injection happens when a parser resolves entities defined in the message, which can read local files or make network requests.
  Parser configuration that disables document type definitions and external entities prevents it.
  Module 4 (section 4.3) explains it, and the [OWASP XML External Entity Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/XML_External_Entity_Prevention_Cheat_Sheet.html) lists the settings.
- Transport-level security (TLS) protects a message between two servers, but a message may pass through intermediaries that read it.
  WS-Security, a standard from [OASIS](https://www.oasis-open.org/standard/wssv1-1/), protects parts of the message itself with XML signatures, XML encryption, and security tokens such as SAML assertions.
  It provides message-level protection that survives intermediaries.

The [OWASP Web Service Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Web_Service_Security_Cheat_Sheet.html) summarizes these and other points.
New services are rarely built with SOAP, but many organizations still operate SOAP services that new code must call.

### gRPC

gRPC is a remote procedure call framework that uses HTTP/2 and Protocol Buffers, a binary format defined by a schema file.
It is common between internal services.
Its security concerns are:

- Channels should use TLS, and service-to-service calls often use mutual TLS, where both sides present certificates (Module 9, section 9.4).
- Each call still needs authentication, for example a token sent as call metadata, and an authorization check in the service.
  An interceptor, which is code that runs before every call, is a good place for shared checks.
- A Protocol Buffers schema defines types but not business rules, so values still need validation, including size limits.
- A server reflection feature lets clients list the available services, like GraphQL introspection, and should be off where it is not needed.

The [gRPC authentication guide](https://grpc.io/docs/guides/auth/) describes the mechanisms, and the [OWASP gRPC Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/gRPC_Security_Cheat_Sheet.html) lists the risks.

## Webhooks and third-party APIs

APIs also connect to other systems.
In a webhook, a service sends an HTTP request to a URL that a consumer registered, for example when a payment completes.
In a third-party API integration, the application calls an API operated by someone else.
In both cases, the application receives data it does not control.

### Webhook risks

The receiving endpoint is public, so anyone can send it requests.
The main risks are:

- A forged request: without verification, anyone who knows the URL can claim that a payment succeeded.
- Replay: an attacker who captures a valid request sends it again.
- Unencrypted delivery: the payload can be read or changed in transit.
- Unvalidated payloads: the content is untrusted data, like any other request.

The common defense for forged requests is a signature.
The sender and receiver share a secret.
The sender computes a keyed hash, such as HMAC ([RFC 2104](https://www.rfc-editor.org/info/rfc2104)), over the request body and sends it in a header.
The receiver recomputes the hash over the exact bytes received and compares the values in constant time.
If the signed content includes a timestamp, the receiver can reject old requests, which limits replay.
Requests should be delivered only over HTTPS.
Some senders publish the IP addresses they use, and a receiver can additionally restrict traffic to those addresses, but addresses can change, so this complements signatures and does not replace them.

### Webhook URLs and server-side request forgery

When your application sends webhooks to URLs that users register, the user chooses where your server sends requests.
An attacker can register an internal address, such as a cloud metadata service, and use the server to reach it.
This is server-side request forgery.
Module 12 (section 12.8) and the [OWASP Server-Side Request Forgery Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html) describe the defenses.
They include allowlisting destinations, blocking internal address ranges, restricting redirects, and setting timeouts.

### Consuming third-party APIs

Unsafe consumption of APIs (API10:2023) occurs when an application trusts what another API returns.
Developers often apply careful validation to user input and then trust a partner's response.
A compromised or buggy third party can return unexpected data, redirects to other hosts, or very large responses.

Reasonable controls are:

- Validate responses against an expected schema, as for user input.
- Use TLS, and do not follow redirects to unknown hosts.
- Set timeouts and size limits, and decide in advance how the application behaves when the third party fails.
- Request only the scopes the integration needs, and store the issued credentials as secrets.
- Treat data from the third party as untrusted when it is written to a database, rendered in a page, or passed to another system.

## API security testing

API testing checks that the controls above work against the running API.
Because an API has no user interface to click through, tests send requests directly.
The [OWASP API Security Testing Framework](https://owasp.org/projects/api-security-testing-framework) and the [WSTG GraphQL testing guide](https://wstg.owasp.org/v4.2/4-Web_Application_Security_Testing/12-API_Testing/01-Testing_GraphQL/) describe approaches.

### What to test

- **Authentication.** Call endpoints without a token, with an expired token, and with a token for another API.
- **Object-level authorization.** Authenticate as user A, then request user B's objects by changing identifiers.
  This single test finds the most common API flaw.
- **Function-level authorization.** Call administrative endpoints as an ordinary user and try other HTTP methods on each path.
- **Property-level authorization.** Send extra properties such as `role` in update requests and check which fields responses return.
- **Rate limits.** Check that limits trigger where expected and cannot be bypassed by changing a header or an IP address.
- **Input handling.** Send oversized, malformed, wrongly typed, and unexpected content.
  Fuzzing automates this by generating many variations of valid requests.
- **Business logic.** Try skipping steps or repeating operations in a workflow.
  Module 11 (section 11.7) covers business logic testing, and the [WSTG introduction to business logic testing](https://wstg.owasp.org/v4.2/4-Web_Application_Security_Testing/10-Business_Logic_Testing/00-Introduction_to_Business_Logic/) explains the approach.

Authorization tests need at least two ordinary users and one administrator, and for multi-tenant systems, users in two tenants.
Module 3 (section 3.5) describes authorization testing.

### Using the API description

An OpenAPI document lists every endpoint, method, and parameter.
Test tools can read it to generate requests, and tests can check that the running API behaves as the description says.
Differences between the description and the running API can reveal undocumented endpoints, which relates to inventory management.

### Testing continuously

Tests that run in a continuous integration pipeline catch regressions, such as a new endpoint without an authorization check.
Useful automated checks include schema validation of requests and responses, authorization tests from a permissions matrix, and scans with tools such as [OWASP ZAP](https://www.zaproxy.org/).
Automated scanners find missing headers and some injection flaws.
They find authorization flaws poorly, because they do not know which user may access which object, so these need tests written for the application.
[OWASP crAPI](https://owasp.org/projects/crapi) is a deliberately vulnerable API for practicing the techniques safely.

## Worked example: reviewing an invoice endpoint

A team reviews a new endpoint in a billing API:

```http
GET /api/v2/invoices/987654
Authorization: Bearer <access token>
```

The review asks questions in the order of this chapter.

1. **Inventory.** Is `v2` in the API inventory, and is an older `v1` of the same endpoint still reachable?
2. **Authentication.** Does the API verify that the token was issued by the expected authorization server, is meant for this API, and has not expired? It must not only decode the token.
3. **Scope.** Does the token carry a scope such as `invoices:read`? The scope shows that the client may read invoices in general.
4. **Object-level authorization.** After loading invoice 987654, does the code check that the authenticated user may read that invoice? A user changing the number in the URL must not receive another customer's invoice.
5. **Property-level authorization.** Does the response contain only the fields this role needs? An internal cost field or the customer's full payment details should not be returned just because they exist in the database object.
6. **Resource consumption.** Does the invoice list endpoint cap the page size, and is there a rate limit per client?
7. **Errors.** Does a request for a missing or forbidden invoice return a generic response without internal details?

Finding the missing object-level check in step 4 matches API1:2023 Broken Object Level Authorization.
The team fixes it in the shared authorization layer so that other endpoints benefit.
It then adds a regression test that logs in as one user, requests another user's invoice, and expects a denied response.
Doing so connects the risk, the control, and the test.
