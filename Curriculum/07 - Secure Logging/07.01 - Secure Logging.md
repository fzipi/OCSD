# Module 7 - Secure Logging

This outline defines the secure logging knowledge assessed in Module 7.

## 7.1 Purpose of security logging and events to log

- The purposes of security logs: detecting attacks, investigating incidents, and supporting accountability
- Security logs compared with error, performance, and debugging logs
- Insufficient logging and alerting as a risk category (OWASP Top 10:2025 A09)
- Authentication events, including successful and failed attempts
- Authorization decisions, especially denials
- Input validation failures and attempts to bypass security controls
- Session management events, administrative actions, and changes to sensitive data
- Unexpected errors and failures of security controls, including those described in Module 6
- Application, server, and operating system logs as different sources

## 7.2 Contents of a log entry

- The information needed to reconstruct an event: when, where, who, what, and the outcome
- Timestamps in UTC or with an explicit time zone, from synchronized clocks
- Identity of the user, service, or system that acted
- Source of the request, such as the client address
- Correlation identifiers that connect the entries of one request across services
- Structured, machine-readable formats and a consistent vocabulary for events

## 7.3 Sensitive data in logs

- Data that must not be logged: passwords, session tokens, API keys, encryption keys, and other secrets
- Personal data, payment card data, health data, and government-issued identification numbers
- The principle of logging only what is necessary
- Masking, hashing, tokenization, and field-level exclusion as controls
- Logs as a high-value asset that inherits the protection requirements of the data they contain
- Data classification and retention of logs are covered in Module 8 (sections 8.1 and 8.5)

## 7.4 Log injection and log protection

- Log injection and log forging through newline, control, and format characters in logged data
- Encoding or neutralizing untrusted data before it is written to a log
- Parameterized log messages and structured formats that separate data from message text
- Access control on logs, with read-only access for most users
- Protection of log integrity and detection of tampering
- Transmission of logs to a separate system so a compromised application cannot erase them

## 7.5 Logging libraries and log levels

- Use of established logging libraries instead of custom code
- Vulnerabilities in logging libraries, including the 2021 Log4Shell vulnerability in Log4j
- Keeping logging libraries updated and avoiding unsafe configuration features
- Log levels as a way to filter entries by importance
- Verbose diagnostic levels and their risk in production
- Security events that must be recorded regardless of the configured verbosity

## 7.6 Monitoring and alerting

- The difference between logging, monitoring, and alerting
- Why logs that nobody reviews do not detect attacks
- Central collection of logs from many components
- Alerts for suspicious events, and the effect of too many false alarms
- The developer's role: producing the events that monitoring depends on
