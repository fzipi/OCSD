# Supplementary reading - Secure Logging

This reading teaches the topics in the Module 7 body of knowledge.
It is written for developers who are new to security.
Module 6 covers how errors are handled and what users see.
This module covers what the application records.

## 7.1 Purpose of security logging and events to log

A log is a record of events that happened in a system.
Security logs are a particular kind of log.
They record events such as authentication decisions, access control decisions, and attempts to get around security controls.
Their purpose is to help detect an attack while it happens, to investigate it afterward, and to show who did what.
They differ from error logs and performance logs, which help developers and operators keep the system working.
The OWASP Application Security Verification Standard (ASVS) 5.0.0 makes the same distinction in its chapter V16.

### Why insufficient logging is a risk

OWASP Top 10:2025 A09, Security Logging and Alerting Failures, describes what happens when logging is missing or weak.
Examples from its description are:

- Logins, failed logins, and high-value transactions are not logged, or only successes are logged
- Warnings and errors produce no log message or an unclear one
- Logs are not protected from tampering
- Logs are stored only locally
- Nobody monitors the logs for suspicious activity

Without these records, a breach can run for a long time unnoticed.
After a breach, the investigators cannot say what the attacker did or what data they reached.

### Events to log

A useful starting list for a web application is:

- Authentication events, both successful and failed, including the method used
- Authorization decisions, especially denials
- Input validation failures and other attempts to bypass controls, such as business logic checks
- Session events such as creation, expiry, and forced logout
- Administrative actions such as role changes and configuration changes
- Creation, change, and deletion of sensitive data
- Unexpected errors and failures of security controls, such as a failed TLS connection to a backend service

ASVS requirement 16.3.4 asks for the last item, and Module 6 explains how such failures should be handled.
Each application has its own risks, so the list should be defined in the application's documentation and kept current.
ASVS 16.1.1 asks for an inventory of what is logged at each layer, where it is stored, who can access it, and for how long.

### Different sources of logs

Application logs come from the code the team writes.
Server and framework logs come from the web server, the application server, and the database.
Operating system logs come from the host, and cloud and container platforms produce their own.
An investigation usually needs more than one of them, so developers should know which logs exist and what each records.

## 7.2 Contents of a log entry

A log entry is only useful if it answers the questions an investigator would ask.
ASVS 16.2.1 calls them when, where, who, and what.
A good entry therefore contains:

- A timestamp
- The component and host where the event happened
- The identity of the user, service, or system involved
- The action and the resource it affected
- The outcome: success or failure
- The source of the request, such as the client IP address
- A correlation identifier

Example of a structured entry:

```json
{
  "time": "2026-03-14T09:21:07Z",
  "event": "authz.denied",
  "user": "u-48213",
  "action": "read",
  "resource": "invoice/4711",
  "source_ip": "203.0.113.25",
  "request_id": "b3f9c1e2-5a7d-4e0b-9c64-1f2a3d5e7b90"
}
```

### Time

Clocks on different servers drift apart, which makes a timeline of events unreliable.
Synchronize the clocks of logging components.
Record timestamps in UTC or with an explicit time zone offset, as ASVS 16.2.2 describes.

### Correlation identifiers

One user request often passes through several services.
A correlation identifier is a unique value created when the request enters the system and passed to every service that handles it.
Each service includes it in its log entries.
An investigator can then collect all entries of one request across all components.
The same value can be shown to the user in a generic error message, as described in Module 6 (section 6.3).
W3C Trace Context is a standard for passing such identifiers between services.

### Structured formats

Free text is difficult for tools to search.
A structured format such as JSON, with consistent field names, lets a log tool filter and combine entries reliably.
ASVS 16.2.4 asks that logs can be read and correlated by the log processor in use, preferably in a common format.
The OWASP Application Logging Vocabulary Cheat Sheet suggests consistent event names so that the same event is recognizable across applications.

## 7.3 Sensitive data in logs

Logs are easy to forget as a place where secrets accumulate.
Anyone who can read a log file can read what is in it.
CWE-532, insertion of sensitive information into a log file, is a mapped weakness in A09.

### What must not be logged

- Passwords and other credentials, including those mistyped into the username field
- Session tokens, API keys, and access tokens
- Encryption keys and other secrets
- Payment card numbers and similar payment data
- Personal data, health data, and government-issued identification numbers beyond what the law and the purpose permit

ASVS 16.2.5 says that logging should depend on the data's protection level.
Some data may never be logged, such as credentials or payment details.
Other data, such as session tokens, may be logged only in masked or hashed form.
Because logs may contain sensitive data despite these rules, they are treated as a high-value asset (Module 8, section 8.1 covers data classification).

### Techniques

- Exclude the field entirely, which is the safest choice
- Mask part of the value, such as showing only the last four digits of a card number
- Replace the value with a hash so entries about the same value can be matched without revealing it
- Replace the value with a token that points to the real value in a protected store

Log only what is needed for the purpose.
For example, log the user identifier instead of the full profile, and log that a token failed validation instead of the token.
The easiest mistake is logging an entire request or object for debugging.
Such logging captures every field, including passwords.
Module 8 (section 8.5) covers how long logs may be kept and when they must be deleted.

## 7.4 Log injection and log protection

### Log injection

Log injection happens when untrusted data is written to a log without being neutralized (CWE-117).
Suppose the application logs the username a visitor entered, and the visitor enters:

```text
alice
2026-03-14T09:30:00Z INFO user=admin action=login outcome=success
```

The line break lets the visitor create a second line that looks like a real entry.
This is called log forging.
It can hide an attack, blame another person, or confuse log analysis.
Other control characters can corrupt the display of a log in a terminal or a viewer.
If the log viewer is a web page that does not encode what it shows, the injected data can even attack the person reading it.

Controls are:

- Encode or remove line breaks and control characters from untrusted values before logging
- Use a structured format such as JSON, where the logging library escapes values
- Use parameterized log calls, where the message is fixed and values are passed separately, instead of building messages by concatenating strings
- Encode log data for the context in which it is displayed, as ASVS 16.4.1 requires

```python
# Risky: user input becomes part of the message text
logger.info("Login failed for " + username)

# Better: fixed message, value passed separately
logger.info("Login failed for user %s", username)
```

Parameterized calls are not enough on their own if the library does not neutralize line breaks.
A structured formatter or an explicit encoding step is still needed.
Untrusted input is covered in Module 4.

### Protecting logs

Logs are targets.
An attacker who has broken into a system wants to erase the traces, and may also read logs for secrets and internal information.
Protect them in these ways:

- Restrict access: read-only for most people, and separate rights to administer the logging system
- Prevent modification, for example with append-only storage
- Detect tampering, for example with hash chains or signed entries
- Send logs to a logically separate system, so a breach of the application does not let the attacker rewrite its history (ASVS 16.4.3)
- Record access to the logs themselves

OWASP A09 also recommends audit trails with integrity controls, such as append-only database tables.
The point of a separate system is that the application should be able to add entries but not alter or delete the ones it has already sent.

## 7.5 Logging libraries and log levels

### Use established libraries

Write logs through a well-known logging library or the logging features of the framework, not through hand-written file code.
Libraries handle concurrency, rotation, formatting, and output destinations.
Examples include `logging` in Python, SLF4J and Log4j in Java, and Winston in Node.js.

### Libraries can be vulnerable

Logging code processes attacker-controlled text all the time, so flaws in it are serious.
The best-known case is Log4Shell, CVE-2021-44228, in the Apache Log4j 2 library.
In affected versions, certain strings in logged data, such as a JNDI lookup expression, were interpreted by the library and could lead to remote code execution.
Simply logging a value an attacker controlled, such as an HTTP header, was enough.
The Apache Log4j security page lists this and later issues in the library.

The lessons are general:

- Keep logging libraries up to date, and track them as dependencies (see Module 10, section 10.3)
- Do not enable features that interpret log content, such as lookups, unless they are needed
- Treat logged values as data and never as code or templates

### Log levels

Most libraries have levels that classify entries by importance, such as `DEBUG`, `INFO`, `WARN`, and `ERROR`.
A configured level acts as a filter: entries below it are dropped.
The exact names and the rules for choosing a level are conventions of the library and the team, not a security standard.
Two points matter for security:

- Verbose levels such as `DEBUG` can include request details and secrets, so they should not be enabled in production by default
- Security events must be recorded whatever the configured verbosity, so they should not be filtered out by lowering the level

## 7.6 Monitoring and alerting

Logging records events.
Monitoring is the ongoing review of those records for signs of trouble.
Alerting notifies people when a pattern needs action.
The A09 category name includes alerting because logs that nobody reads do not stop an attack.

### Central collection

Components that log to local files are hard to search together and are easy to erase after a breach.
Log shippers and agents send entries to central storage, where tools can search, correlate, and alert across services.
Central storage also supports the separation described in section 7.4.
Security information and event management (SIEM) tools are one kind of platform for this.
Operating them is the work of security operations teams.
For a developer, the relevant point is that the entries the application produces must be useful to them.

### Alerts that people act on

Alerts must go to someone who can respond, with a defined procedure.
Too many false alarms train people to ignore alerts.
Choose events that signal real problems, so that alerts stay meaningful.
The OWASP AppSensor project describes detection points inside the application, such as a request that no normal user could generate, which produce events with few false positives.

### Developer's role

Developers decide which events the application emits and how clear they are.
A security-relevant failure that is not logged cannot be detected, no matter how good the monitoring system is.
A10 notes the same relationship: an application that mishandles an error may be unaware of it and so unable to log it.

### Worked example

A team reviews the login feature.
The code logs successful logins only, writes the submitted username with string concatenation, and records the whole request body on failure for debugging.

The review finds three problems.
Failed logins are not logged, so a password-guessing attack leaves no trace (section 7.1).
The username can contain line breaks, which allows log forging (section 7.4).
The request body contains the submitted password, which is stored in the logs (section 7.3).

The fix logs both outcomes with a structured entry containing the event name, the user identifier or the attempted username as an encoded value, the source address, and a correlation identifier.
The password is never logged.
The entries are sent to central storage that the application cannot modify.
An alert fires when many failures occur for one account or from one address in a short time.
