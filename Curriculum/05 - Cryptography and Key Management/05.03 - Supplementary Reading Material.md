## 5.1 Security properties of cryptography

Cryptography is the practice of protecting information with mathematical techniques.
It is not one tool but a set of building blocks.
Each block supports one or more security properties.

Confidentiality means that only authorized parties can read data.
Encryption provides it by turning plaintext, the readable data, into ciphertext that is unintelligible without the key.
Examples include encrypted backups, encrypted database fields, and encrypted traffic.

Integrity means that unauthorized or accidental changes to data can be detected.
Hash functions, message authentication codes (MACs), and digital signatures support it.
Integrity does not hide data; it only reveals modification.

Authenticity means that the origin of data or the identity of a party can be verified.
MACs, digital signatures, and certificates support it.
Encrypted traffic is not authentic traffic: without authentication, a client can encrypt data to an attacker.

Non-repudiation means that a party cannot plausibly deny having produced a message or approved an action.
Digital signatures support it because only the holder of the private key can create a valid signature.
In practice, it also depends on how the key was issued, how well it is protected, and whether logs and records back up the claim.
A MAC cannot provide non-repudiation, because every party that can verify a MAC can also create one.

Three principles apply to every mechanism in this module:

- The algorithm is public and reviewed; the security rests on keeping the keys secret.
- Using a strong algorithm incorrectly still produces an insecure system.
- Cryptography does not replace authentication, authorization, or secure design.
  It also does not protect data after a legitimate recipient decrypts it, or after a stolen key unlocks it.

## 5.2 Encoding, encryption, and hashing

Developers often mix up three different transformations.
The table summarizes them.

| Transformation | Reversible | Needs a secret | Purpose |
|---|---|---|---|
| Encoding | Yes | No | Represent data in a format that a system or protocol can handle |
| Encryption | Yes, with the key | Yes | Keep data confidential |
| Hashing | No | No | Produce a fixed-length fingerprint to compare or verify data |

Encoding converts data from one representation to another.
Base64, hexadecimal, and URL encoding are common examples.
Anyone can reverse an encoding without a key.
Base64 text that looks scrambled is as readable as plaintext.
A Base64-encoded key or password is therefore not protected.

Encryption uses an algorithm and a key to transform plaintext into ciphertext.
Only a party with the right key can reverse it.

Hashing uses a hash function to turn input of any length into a fixed-length digest.
It has no key and cannot be reversed.
Hashing is used to detect changes and to store passwords with dedicated algorithms (see section 5.5).

A quick way to choose:

- To send binary data through a text-only channel, use encoding.
- To keep data secret and recover it later, use encryption.
- To check that data has not changed, use a hash, a MAC, or a digital signature.
- To store a password so that it can be verified but not recovered, use a password-hashing algorithm.

## 5.3 Encryption

### Symmetric and asymmetric cryptography

Symmetric cryptography uses the same secret key to encrypt and decrypt.
It is fast and suited to large amounts of data, such as files, database fields, and backups.
The difficulty is that both parties must hold the key and share it without exposing it.

Asymmetric cryptography uses a key pair.
The public key can be shared freely, and the private key must stay secret.
Depending on the algorithm, the pair is used for encryption, key exchange, or digital signatures.
It is much slower than symmetric cryptography and is usually applied to small values.

Real systems combine the two in a hybrid design.
Asymmetric cryptography establishes or protects a symmetric key, and that key then protects the bulk data.
TLS and encrypted email follow this pattern.

Common algorithm families:

- AES is the most widely used symmetric cipher.
- ChaCha20 is a modern symmetric cipher that performs well in software, including on devices without AES hardware acceleration.
- RSA and elliptic curve cryptography are the widely used asymmetric families.

Minimum key sizes change as attacks and hardware improve.
Check current guidance, such as NIST SP 800-57 and SP 800-131A, instead of memorizing numbers.
At the time of writing, 128-bit symmetric keys and 2048-bit RSA keys are generally treated as the lowest acceptable sizes.

### Authenticated encryption

Encryption alone hides data but does not stop modification.
An attacker who cannot read ciphertext may still change it so that it decrypts to something different, and some modes make those changes predictable.

Authenticated encryption with associated data (AEAD) solves this by providing confidentiality and integrity in one operation.
Decryption fails if the ciphertext, or the associated data that travels with it, was altered.
Common AEAD constructions are AES-GCM and ChaCha20-Poly1305.
The recommended approach is to use an AEAD mode from a well-reviewed library.

Two older choices need special care:

- Electronic Codebook (ECB) mode encrypts every block independently, so identical plaintext blocks give identical ciphertext blocks.
  Patterns in the data remain visible, so ECB is not suitable for general use.
- Cipher Block Chaining (CBC) mode hides patterns but gives no integrity protection.
  If a developer must use it, the data needs a separate MAC, applied to the ciphertext (encrypt-then-MAC).

### Nonces and initialization vectors

Many modes need a value that changes with each encryption.
It is called a nonce ("number used once") or an initialization vector (IV).
It is stored or sent with the ciphertext and does not need to be secret.

Two rules matter:

- The value must never repeat for the same key.
- Some modes, such as CBC, also require the IV to be unpredictable, so it should come from a secure random number generator.

Repeating a nonce in AES-GCM or ChaCha20-Poly1305 is a severe failure.
It can reveal relationships between plaintexts and allow an attacker to forge valid messages.
Libraries that generate and manage nonces for the caller remove much of this risk.

### Use libraries, not custom designs

Cryptographic algorithms and protocols are designed and reviewed by specialists over years.
Small deviations, such as combining primitives in a new way, often introduce weaknesses that the author cannot see.
Use the platform's cryptography API or a high-level library such as libsodium, and use its default modes where it offers them.
Prefer a library function that performs a complete operation, such as "encrypt and authenticate this message", over assembling cipher, mode, padding, and MAC by hand.

## 5.4 Hash functions, MACs, digital signatures, and certificates

### Hash functions

A cryptographic hash function should have three properties:

- Preimage resistance: given a digest, it is infeasible to find an input that produces it.
- Second-preimage resistance: given an input, it is infeasible to find a different input with the same digest.
- Collision resistance: it is infeasible to find any two different inputs with the same digest.

SHA-2 (for example SHA-256) and SHA-3 are the current families for security purposes.
MD5 and SHA-1 have practical collision attacks and must not be used where an attacker could benefit from a collision, such as signatures, certificates, and integrity checks.

A hash proves integrity only if the digest itself cannot be replaced.
If an attacker can alter a downloaded file and the hash published next to it, the check proves nothing.
To protect against that, use a MAC, a digital signature, or a hash obtained over a separate trusted channel.

### Message authentication codes

A MAC is computed from a message and a secret key.
The receiver recomputes it with the same key.
A match shows that the message was not changed and that its sender held the key.

HMAC builds a MAC from a hash function, for example HMAC-SHA-256.
It is standardized in RFC 2104 and is the standard choice when a MAC is needed.
Do not build a MAC by hashing a key and a message together, because some hash functions allow length extension attacks (section 5.6).
Comparing MACs or other secrets must use a constant-time comparison function.

Typical uses are signed webhook payloads, signed cookies, and request signing between services that share a secret.

### Digital signatures

A digital signature is created with a private key and verified with the matching public key.
It provides integrity and authenticity, and, with sound key control, supports non-repudiation.
Typical uses are signed software releases, signed documents, code signing, and signed tokens.

The key difference from a MAC is who can create the value:

| Property | MAC | Digital signature |
|---|---|---|
| Key type | One shared secret key | Private key to sign, public key to verify |
| Who can create it | Everyone who can verify it | Only the private key holder |
| Supports non-repudiation | No | Yes |
| Relative speed | Faster | Slower |

Common choices include RSA with PSS padding, ECDSA, and EdDSA (Ed25519).
Elliptic curve schemes have smaller keys and signatures than RSA at similar strength.
Ed25519 is specified in RFC 8032 and does not need a fresh random value for each signature, which removes one implementation risk of ECDSA.
Both ECDSA and Ed25519 are accepted choices; follow the library's and the standard's current recommendations.
For RSA encryption, OAEP padding is recommended, and for RSA signatures, PSS padding is recommended, because older PKCS#1 v1.5 padding has known weaknesses.

Always verify a signature or MAC before the signed data is parsed or used.
Using the data first and checking later lets an attacker feed it to the application.

### Certificates and certificate authorities

A public key says nothing about who owns it.
An X.509 certificate binds a public key to an identity, such as a domain name, an organization, or a device.
It contains the subject, the public key, the issuer, a validity period, extensions such as subject alternative names, and the issuer's signature.

A certificate authority (CA) is a trusted party that verifies identities and signs certificates.
Operating systems and browsers ship with a set of trusted root CAs.
Most server certificates are signed by an intermediate CA, which is signed by a root.
The chain of signatures from the certificate to a trusted root is called the chain of trust.

Validating a certificate means checking that:

- The chain leads to a trusted root and every signature is valid.
- The certificate is within its validity period.
- The hostname or identity being contacted matches the certificate.
- The certificate has not been revoked.

Revocation information is published in certificate revocation lists (CRLs) or answered by the Online Certificate Status Protocol (OCSP).
Certificate lifecycle practices, pinning, and mutual TLS are covered in Module 9.

## 5.5 Password hashing and random numbers

### Password hashing

Systems that verify passwords should store a hash and never the password, so that a database leak does not reveal passwords directly.
General-purpose hashes such as SHA-256 are designed to be fast.
An attacker with a stolen hash list can test billions of guesses per second on modern hardware.

Password-hashing algorithms are deliberately slow and, in some cases, memory-hungry, which makes each guess expensive.
The recommended algorithms are:

- Argon2id (specified in RFC 9106)
- scrypt
- bcrypt

PBKDF2 is also accepted in some standards, with a high iteration count.
The OWASP Password Storage Cheat Sheet lists current recommended parameters.
Review those parameters periodically and increase them as hardware gets faster.

A salt is a unique random value generated for each password and stored alongside its hash.
It does not need to be secret.
It has two effects:

- Two users with the same password get different hashes.
- Precomputed tables, such as rainbow tables, become useless, because the attacker would need a table for every salt.

A salt does not make a weak password strong.
The cost of the hashing algorithm is what slows down guessing of each individual hash.
Dedicated password-hashing libraries generate and store the salt automatically.

Storing passwords with reversible encryption is also a mistake, because anyone who obtains the key can recover every password.
Password policy, rate limiting, and credential recovery belong to Module 2.

### Random numbers

Keys, nonces, salts, session identifiers, and reset tokens all depend on values an attacker cannot guess.
A pseudo-random number generator (PRNG) produces output that looks random from an initial seed, but anyone who learns the seed or enough output may predict later values.
General-purpose generators such as `Math.random()` in JavaScript or `random` in Python are built for speed and statistical quality, not unpredictability.

A cryptographically secure pseudo-random number generator (CSPRNG) is designed so that its output cannot be predicted even when previous output is known.
It is seeded from unpredictable sources of entropy, such as hardware events, collected by the operating system.

Use the operating system's generator, either directly or through a language API:

- Linux and macOS: `getrandom()` or `/dev/urandom`
- Windows: `BCryptGenRandom`
- Python: the `secrets` module
- Node.js: `crypto.randomBytes()` or `crypto.randomUUID()`
- Java: `SecureRandom`

The operating system handles seeding and reseeding.
When an API does not state that it is cryptographically secure, assume that it is not.
Weak or low-entropy random values lead to guessable keys, tokens, and password reset links.

## 5.6 Weaknesses and attacks

### Weak, deprecated, and misused algorithms

Cryptographic algorithms age.
Algorithms and parameters that were once standard, such as DES, 3DES, RC4, MD5, SHA-1, and small RSA keys, are now considered broken or too weak.
Code written years ago often still contains them.
Review algorithm choices against current guidance and replace deprecated ones.

Cipher suites for TLS follow the same logic and are covered in Module 9.
In short, CBC-based suites, static RSA key exchange, and 3DES are discouraged, not just unfashionable, and a hardened configuration should follow current recommendations such as the Mozilla guidance linked below.

Other frequent misuse patterns:

- Hardcoded keys and secrets in source code.
  Source code is copied, shared, committed to repositories, and, for client applications, can be decompiled.
- Custom algorithms or custom token and message formats.
- Reused nonces or IVs.
- Encryption without integrity protection.
- Disabling TLS certificate validation to remove a development error.
  The connection stays encrypted, but the client can no longer tell whether it is talking to the real server.
- Assuming TLS protects data once it has arrived, or protects against a compromised endpoint.

### Brute-force and dictionary attacks

A brute-force attack tries every possible key or password.
A dictionary attack tries likely candidates, such as common passwords and leaked passwords.
Feasibility depends on the size of the search space and on the cost of each guess.

A random 128-bit key has too many possible values for any realistic attacker to try all of them.
Human-chosen passwords have far less entropy, so they are the realistic target, especially offline against a stolen hash list.
The defenses are long random secrets, slow password hashing, and rate limiting for online guessing.

### Rainbow table attacks

A rainbow table is a precomputed table that maps hashes back to likely passwords, trading storage for computation time.
It works against unsalted, fast hashes.
Unique salts and a slow password-hashing algorithm defeat it (section 5.5).

### Hash collision attacks

A collision attack finds two different inputs with the same digest.
This breaks collision resistance.
Collisions can be used to create two documents or certificates that share a signature, with one benign and one malicious.
The first public SHA-1 collision, called SHAttered, was published in 2017.
MD5 collisions were demonstrated earlier.
The defense is to use SHA-2 or SHA-3 for signatures and integrity checks.

### Length extension attacks

Some hash functions, including MD5, SHA-1, SHA-256, and SHA-512, process input in a way that lets an attacker continue the computation.
Given `hash(secret || message)` and the length of the secret, an attacker can compute a valid hash for the message with extra data appended, without knowing the secret.
This breaks home-made MACs built as `hash(secret || message)`.
HMAC is designed to resist the attack, and SHA-3 is not affected by it.
Use HMAC instead of building a MAC from a plain hash.

### Replay attacks

A replay attack captures a valid message and sends it again later, for example a signed request or an authentication token.
The message is genuine, so a signature or MAC check passes.
Defenses include nonces, timestamps with a short validity window, sequence numbers, and short-lived tokens, combined with server-side tracking of values already used.

### Man-in-the-middle and downgrade attacks

A man-in-the-middle attacker sits between two parties and can read or change their traffic.
Encryption helps only if each side verifies who it is talking to.
That is why certificate validation matters, and why disabling it removes the protection.

A downgrade attack interferes with negotiation so that both parties use an older protocol version or weaker algorithm that the attacker can break.
Defenses are to disable obsolete versions and algorithms on both sides and to refuse insecure fallback.
HTTP Strict Transport Security prevents downgrade from HTTPS to HTTP.
Module 9 covers these settings.

### Padding oracle attacks

Some block cipher modes, notably CBC, pad the last block.
If an application reveals through error messages or timing whether padding was valid, an attacker can send many modified ciphertexts and use those answers to recover the plaintext, without the key.
The root cause is that the application processes unauthenticated ciphertext.
Authenticated encryption rejects modified ciphertext before any padding is examined.
Returning the same generic error for all failures supports that defense.

### Timing side channels

A side channel leaks information from how an operation behaves, not from the algorithm itself.
Timing is the one developers meet most often.
A comparison function that stops at the first mismatching byte takes longer when more leading bytes of a guess are correct, so an attacker who measures response times can recover a MAC or token one byte at a time.
Use the constant-time comparison function that the cryptographic library or platform provides when comparing secrets, MACs, and tokens.
Ordinary equality operators are not safe for this purpose.

### Key theft

Many real incidents involve stolen keys, not broken algorithms.
Common causes are keys committed to repositories, keys written to logs, key files with weak permissions, secrets exposed by build pipelines, and keys stored next to the data they protect.
This is why section 5.7 matters as much as algorithm choice.

## 5.7 Key management

Key management is the set of processes that generate, store, distribute, use, rotate, and destroy keys.
A strong algorithm does not help if its key is predictable, shared too widely, or never changed.

### Key generation

Generate keys with a CSPRNG or with the key generation function of a trusted library or service.
Do not derive keys from predictable values.
If a key must come from a password, use a key derivation function such as PBKDF2, scrypt, or Argon2 with a salt.
Use HKDF to derive several keys from one strong secret.
Use a separate key for each purpose, such as encryption, signing, and authentication, so that a leak in one area does not affect others.

### Key storage

The most common failure is keeping a key next to the data it protects, or in source code, configuration files, logs, or unprotected backups.

Better options, from most to least protected, are:

- A hardware security module (HSM), which stores keys in tamper-resistant hardware and performs operations inside it so that the key is not exposed to the application.
- A cloud key management service (KMS), where the provider manages the keys and the application calls an API to encrypt, decrypt, or sign.
- A secrets manager, which stores secrets centrally, controls and logs access, and delivers them to applications at runtime.
- An operating system key store, which uses built-in protection for keys on a single machine.

Environment variables keep secrets out of source code but remain visible to anything that can read the process environment, so they need operating system access controls and must not be logged.
A key stored in a file needs restrictive permissions, ideally encryption under another key.
Cryptographic keys that merely look scrambled, such as Base64 text, are not encrypted.
Secrets management in deployment pipelines is covered in Module 14.

Many designs use a key hierarchy.
A key-encryption key stored in a KMS or HSM protects the data-encryption keys, which in turn protect the data.
Only the small top-level key then needs the strongest protection.

### Access control and auditing

Give each service access only to the keys it needs.
Log key use and administrative operations, and review those logs.
Where practical, separate the people who manage keys from the people who can read the protected data.

### Key distribution and exchange

Keys must reach their users without exposure or substitution.
Do not send keys by email or chat.
Use an authenticated key exchange protocol, a certificate-validated channel, or a secrets manager.
Diffie-Hellman key exchange lets two parties derive a shared secret over an insecure channel without sending it.
The ephemeral variants used in TLS also give forward secrecy, which Module 9 covers.

### Key rotation

Rotation replaces a key with a new one.
It limits the amount of data exposed if a key is silently compromised and limits how long an old key is useful.
Rotate on a defined schedule, when compromise is suspected, when someone with access leaves, and when guidance changes.

Practical points:

- Automate rotation, because manual rotation is easy to postpone.
- Store a key identifier or version with each piece of encrypted data, so the correct key is chosen for decryption during the transition.
- Allow old and new keys to overlap until all data and clients have moved.
- After rotating a symmetric key, re-encrypt data that must remain readable under the new key.
- Heavily used keys and keys of smaller size warrant shorter lifetimes.
  NIST SP 800-57 gives recommended lifetimes.

### Revocation, decommissioning, and destruction

A compromised key must be revoked and replaced quickly, and anything signed or encrypted with it must be reviewed.
For certificates, revocation uses CRLs or OCSP.

Decommissioning is the orderly retirement of a key.
First mark it inactive, stop new use, remove it from applications, and confirm that nothing still depends on it.
Destruction comes last.
Destroying a key makes all data encrypted only under that key permanently unreadable, so confirm that backups, archives, and required records are covered first.
Deleting a file does not reliably remove a key from disks, backups, or version control history.
Keys held in memory should be cleared when no longer needed, using secure memory facilities where the platform provides them.
Destroying a key on purpose to make data unreadable is called cryptographic erasure and is covered in Module 8.

## Worked example: reviewing a design that stores customer documents

A team plans to let customers upload documents and keep them encrypted in cloud storage.
The design notes say:

- Documents are encrypted with AES in CBC mode using a key defined in a configuration file in the repository.
- The IV is a fixed value in the same file.
- Download links are protected by `sha256(userId + secret)` as a token.
- User passwords are stored as SHA-256 hashes.

A reviewer who knows the material in this chapter would raise these points:

1. A key in the repository is exposed to everyone who can read the code and to everything the repository is copied to (section 5.7).
   The key should come from a KMS or secrets manager, with a key identifier stored with each document so it can be rotated.
2. A fixed IV is reused for every document, and CBC needs an unpredictable IV (section 5.3).
   An AEAD mode with a fresh nonce for each document would also detect tampering, which CBC alone does not.
3. The download token is a home-made MAC of the form `hash(secret || message)`, which is exposed to length extension (section 5.6).
   Use HMAC with a secret key stored as in point 1, compare the result with a constant-time function, and include an expiry time to limit replay.
4. SHA-256 is a fast hash and is not suitable for passwords (section 5.5).
   Use Argon2id, scrypt, or bcrypt through a library, and let it handle the salt.
5. The design does not say how random values are produced.
   Keys, nonces, and salts must come from a CSPRNG (section 5.5).

None of these changes require a new algorithm.
Each one replaces a custom or outdated choice with a standard one, and each moves the key out of the code.

## Further reading

Standards and specifications:

- [NIST SP 800-57 Part 1 Rev. 5: Recommendation for Key Management](https://csrc.nist.gov/pubs/sp/800/57/pt1/r5/final) covers key lifecycle and recommended key lifetimes.
- [NIST SP 800-131A Rev. 2: Transitioning the Use of Cryptographic Algorithms and Key Lengths](https://csrc.nist.gov/pubs/sp/800/131/a/r2/final) lists which algorithms and key lengths are acceptable or disallowed.
- [NIST SP 800-38D: Recommendation for Block Cipher Modes of Operation, Galois/Counter Mode (GCM) and GMAC](https://csrc.nist.gov/pubs/sp/800/38/d/final) is the specification of AES-GCM, including nonce requirements.
- [RFC 2104: HMAC](https://www.rfc-editor.org/rfc/rfc2104) defines the HMAC construction.
- [RFC 8017: PKCS #1 RSA Cryptography Specifications Version 2.2](https://www.rfc-editor.org/rfc/rfc8017) defines OAEP and PSS padding.
- [RFC 8032: Edwards-Curve Digital Signature Algorithm (EdDSA)](https://www.rfc-editor.org/rfc/rfc8032) defines Ed25519.
- [RFC 9106: Argon2](https://www.rfc-editor.org/rfc/rfc9106) defines the Argon2 password-hashing function.
- [RFC 5280: Internet X.509 Public Key Infrastructure Certificate and CRL Profile](https://www.rfc-editor.org/rfc/rfc5280) defines the X.509 certificate format.

Practical resources:

- [libsodium documentation](https://libsodium.gitbook.io/doc/) describes a high-level library designed to make misuse difficult.
- [Mozilla SSL Configuration Generator](https://ssl-config.mozilla.org/) produces hardened TLS configurations that follow current recommendations.
- [SHAttered](https://shattered.io/) describes the first practical SHA-1 collision.
- [Cryptopals Crypto Challenges](https://cryptopals.com/) are optional exercises that show how common mistakes, such as ECB, CBC padding oracles, and length extension, are exploited.

Books:

- Ivan Ristić, [Bulletproof TLS and PKI](https://www.feistyduck.com/books/bulletproof-tls-and-pki/), a commercial book on TLS and public key infrastructure.
